## 結論（先に3行）

1. **105 件は欠陥の全体像ではなく、見えている部分。** month 精度の event 日付は**大半が「旧暦の月番号をそのまま ISO の月に置いた未換算値」**で、
   照合可能な 1389 フィールドのうち **1151（83%）が未換算**。うち旧暦十一月・十二月にあたる 105 件は年もずれるので目立っただけで、A と C は同じ1つの欠陥の2つの見え方。
2. **C は「方針が未決定」ではなく「決定済みの規約が event に適用されていない」。** 多数月方式は
   [AI_RESEARCH_LESSONS.md](../../process/AI_RESEARCH_LESSONS.md) の 3節・9節で規約として書かれ、`ages` には 2026-07-21 に適用済み（[QA_HISTORY.md](../../QA_HISTORY.md)）。
   したがって判断は「規約を適用するか」対「month 精度 event については規約を明示的に撤回するか」であって、新しい規約を選ぶ話ではない。
3. **A だけを「年に +1」して直すことはできない。** 旧暦十二月の実太陽暦は翌年 **1 月**なので、A を直すと月も動く＝ A の訂正は
   month 精度 event に太陽暦の月意味論を持ち込む決定そのもの。C を後回しにすると「同じ month 精度なのに一部だけ太陽暦」が残る。

## 1. month 精度 event 日付の実態

対象は `events[]` の `date`/`startDate`/`endDate` で ISO 実値を持つもの（month 2424・day 1321・year 937 フィールド）。
このうち **CE かつ note 等に旧暦月が書かれていて照合できる 1389 フィールド**の内訳:

| 区分 | 件数 | 内容 |
|---|---|---|
| **未換算**（ISO 月＝note の旧暦月） | **1151** | うち **A: 年またぎ 105**／**C: 年は同じで月がずれる 1008**／偶然一致 38 |
| 換算済みらしい（ISO 月≠note の旧暦月） | 238 | **多数月方式 147**（同年紀年 139・前年紀年 8）／朔方式 9／どちらとも不一致 82 |

- 「どちらとも不一致 82」は、期間イベントの note に複数の旧暦月が出てきて開始・終了がどの月に対応するか機械では決まらないもの（＝ノイズ）。
- **同じデータセット内で換算方式が混在している**（未換算 1151・多数月 147・朔 9）。統一されていたことは一度もない。
- 照合できない month 精度フィールドが別に 1035 ある（**note に旧暦月が書かれていない 969**＋BCE 66。BCE は
  `ADDITIONAL_SCHEMA.md` に漢初の年始が冬十月である扱いを含む別規約があるため今回の対象外とした）。
  **この 1035 は本調査の方法では判定不能**で、未換算がさらに含まれている可能性が高い。105 も 1151 も下限。

**day 精度は逆に、おおむね換算済み**（note に旧暦月がある 1144 件のうち 1074 が ISO→旧暦の逆変換で一致）。
`reigns[]`・`ages` も太陽暦換算済み。つまり**取り残されたのは month 精度の event だけ**。

## 2. 規約側の確認（C は既決）

| 文書 | 記述 |
|---|---|
| `AI_RESEARCH_LESSONS.md` 3節 | 「旧暦月だけ判明している日付の月精度換算も同じく**多数月方式**（例: 旧暦九月→大半が重なる 10 月）で統一する」 |
| `AI_RESEARCH_LESSONS.md` 9節 | 「旧暦十一月・十二月は年またぎする。**ISO 年は必ず sxtwl の太陽暦出力から取る**（年注記は紀年ラベル年）」 |
| `data/schema/ADDITIONAL_SCHEMA.md` | 「**month/day precision では実際のユリウス暦時点が属する年を使う**…year precision では紀年（元号の元年等）の対応年を使う」（BCE 規約の節だが年の取り方の一般則） |
| `docs/QA_HISTORY.md` | ages 生没年の ISO 正規化（2026-07-21）で「旧暦月番号の転記 9 件（**太陽暦多数月へ補正**）」「太陽暦年が繰り上がった 3 件」を実施済み |

規約は「month 精度でも ISO は太陽暦、月は多数月方式」で確定しており、`ages` では実際にその通り直されている。

## 6. 判断を仰ぐ点（2026-08-02 に決着・**案1／進め方(b)** をユーザーが承認）

### (1) month 精度 event の換算方針

| 案 | 内容 | 評価 |
|---|---|---|
| **案1（推奨）** | 既存規約どおり多数月方式を A+C の 1113 フィールドへ適用 | 全フィールドで ISO＝太陽暦に統一され、`ages`/`reigns`/day 精度と揃う。3節の矛盾も解消。欠点は note の「十二月」と ISO の「1月」が並ぶ見え方 |
| 案2 | A の 105 件だけ訂正 | 「同じ month 精度なのに一部だけ太陽暦」が 1008 件残る。中途半端で、再発検出のゲートも書けない |
| 案3 | month 精度 event は旧暦年月をそのまま置くと追認 | A は誤りでなくなるが、`ages`/`reigns`/day 精度と二重基準になり 3節の共存が説明できない。AI_RESEARCH_LESSONS 3・9節と ADDITIONAL_SCHEMA の書き換えが必要（決定の撤回） |

### (2) 案1を採る場合、1113 フィールドを機械適用してよいか

[CONSTRAINTS.md](../../process/CONSTRAINTS.md) の「スクリプトによるデータの自動生成は禁止（日数計算等の機械的な計算補助はOK）」との境界。
本件の換算は「既に個別調査で確定している旧暦年月」を sxtwl で太陽暦へ写す計算補助であり、新しい判定を生まない一方、
**どの旧暦月を根拠にするかを正規表現で note から取っている**点は機械判定にあたる。案としては:

- **(a) 全件機械適用＋抜き取り検証**: 105+1008 を一括変換し、A 105 件と C から無作為抽出した数十件を原典で裏取り
- **(b) A は個別確認・C は機械適用**: 年が動く A だけ原文の干支・記事順で裏取りし、月だけ動く C は機械適用
- **(c) 全件個別確認**: 1113 フィールドを人物ごとに確認（Issue #33 と同じやり方だが規模が2桁違う）

### (3) 表示側をどうするか

サイトの個別ページ「在位中の出来事」は ISO の年月をそのまま「〇年〇月」と出し、ソートキーにも使っている（`site/src/lib/emperors.ts` の `eventDateOf`）。
換算後は「旧暦十二月の事件が翌年1月と表示される」ため、note の元号日付との突き合わせが読者に見えなくなる。
`note` に元号日付が残っているので破綻はしないが、月精度の日付ラベルに旧暦月を併記するかは別途判断がいる。

### (4) 恒久チェック（方針決定後）

- `check_event_reign_range`・`check_bce_event_years` を `startDate`/`endDate` にも広げる（今回の 105 件が素通りした直接の原因）
- 新チェック: month 精度で note の旧暦月が一意に取れる場合、ISO 年月が多数月方式の結果と一致すること
  （案3を採るなら逆向き＝旧暦月と ISO 月の一致を assert する）
- 検出の限界（note に旧暦月が無い 969 フィールド）は機械では埋まらない。埋めるなら `source.page` から原文を引き直す個別作業になる

## 7. 訂正の前に分かった「触ってはいけないもの」

当初は「未換算 1113 フィールドを多数月方式で一括換算」を想定していたが、対象の切り方を厳しくする過程で
**偽陽性が混ざっていた**ことが分かった。適用条件を決めたのは次の2つの発見:

- **note に複数の旧暦月が出てくる期間イベント**（445 フィールド）は、ISO 月がたまたまそのうちのどれかと一致するだけで
  「未換算」とは限らない。どの月に対応するかは記述順を見ないと決まらない
- **日（day）に実値が入っている month 精度フィールド**（39 件）は、**既に太陽暦の日まで換算済み**のことがある
  （例: `wudai-houliang-modi` の `0914-09-23` は乾化四年九月の実日付。ISO 月 9 と旧暦九月の一致は偶然）。
  これを多数月方式で 10 月へ動かすのは改悪になる

そこで「日がプレースホルダ（`-01` または月末）」であることを必須条件にし、複数月のものは記述順から対応月が決まる場合だけ扱った。

## 9. フェーズ5: 残り 193 フィールドの個別判定（2026-08-02・C まで完了）

8節の時点で残していた C 208 件ほかを、**1 件ずつ原典と note で対応月を決めて**片付けた（`apply_phase5.py`）。
判定は 105 フィールドの訂正・88 フィールドの現行維持で決着し、**保留は 0**。
フェーズ3で「原典で対応月を確定できず保留」とした A の 2 件も原典で決着した:

- `jin-huaidi.rebellionSuppressionCount[2].endDate` — 晋書懐帝紀「十二月戊寅，并州人田兰、薄盛等斩汲桑于乐陵」＝永嘉元年十二月
- `liu-song-mingdi.rebellionSuppressionCount[0].endDate` — 宋書明帝紀「十二月己未……刘勔克寿阳，豫州平」＝泰始二年十二月

### 判定の向きを変えた（ここが今回の要）

フェーズ1〜4は「現在値が未換算かどうか」を当てにいっていたが、**閏月のある年は旧暦月 → 太陽暦月が 2 か月ずれる**
（旧暦35年は閏三月があるため 旧暦六月 → `0035-08`）ため、この向きだと**換算済みの値を未換算と誤認する**。
実際 `hou-han-guangwudi` の親征（建武十一年六月出陣）は `0035-08-01` で正しいのに、
「ISO 月 8 ＝旧暦八月の転記」に見えてしまう。

そこでフェーズ5では **「その端点が指すべき旧暦月を原典で決める → 多数月方式で写す → 現在値と比べる」** に統一した。
補助として「現在値が換算済みだとすると元の旧暦月は何か」（逆写像・全月を走査して求める）を
`make_worksheet.py` が出し、note の旧暦月列と突き合わせられるようにした。

### 干支不在クラスの扱いを決めた

フェーズ1・2 で「note の干支が sxtwl の当該旧暦月に実在しない」として機械換算から外した 22 件は、
原典に当たると**月ラベル自体は原文どおり**だった（後漢書桓帝紀「三年春正月己未，大赦天下」・
三国志魏書「九月乙未，大赦」・魏書高祖紀「闰月癸丑，皇子生，大赦天下」など）。
史書暦と sxtwl の朔・置閏の差なので、**month 精度の値は月ラベル基準で換算する**ことにした。
干支は日精度の情報で、月精度フィールドの換算根拠にはしない。

### 判定の過程で分かったこと

- **`0553-08-20`（`liang-xiaoji` の敗死）のように、month 精度でも実日付まで換算済みのものがある**。
  逆変換すると旧暦七月26日で、梁書の記事順（「六月、紀筑連城」の後）と整合する。触ってはいけない
- **`1452-10-13`（`ming-daizong` の福建盗蜂起）は景泰三年閏九月の朔そのもの**。
  旧暦月の正規表現が閏月を除外するため未換算候補として拾われていただけで、値は正しい
- **フェーズ4で巻き戻した 2 件のうち 1 件は巻き戻しが誤りだった**（`jin-huidi` の親征）。
  `endDate 0304-07-30` を「note の己未の実日付」と見たが、逆変換すると旧暦六月12日で、
  永興元年七月己未の実日付は `0304-09-09`。両端とも旧暦七月（多数月 `0304-08`）へ直した
- `wudai-houtang-mingzong` の 6 フィールドは、日に実値がありながら note のどの月とも対応しない値だった
  （例 `0932-06-25` ＝旧暦五月19日。note は長興三年六月の董璋敗死）。month 精度の月初へ直した

## 10. 検出器を作り直した（`check_month_conversion.py`）

Issue #33 のスイープ `sweep_event_iso_year.py` は「ISO 月が note の旧暦月と一致したら未換算」と見なす作りで、
**フェーズ5 を終えた後も 127 件をヒットさせる**（すべて原典で確認済みの正しい値）。閏月による 2 か月ずれと、
期間イベントの note に複数月が出ることが原因で、検出器としてこれ以上は使えない。

そこで判定を逆向きにした検出器 `check_month_conversion.py` を置いた:

1. note に現れるいずれかの旧暦月（紀年年 `y` と年またぎの `y-1` の両方）を多数月方式で写した値と一致すれば OK
2. 一致しなくても、逆変換した旧暦月が note の月に含まれれば OK（実日付まで換算済み・閏月の朔をここで拾う）

## 11. フェーズ6: `YYYY-MM` 形式が丸ごと検査対象から漏れていた

フェーズ5 まで「解消した」と書いた直後、**フェーズ1〜5 のスクリプトがすべて
`^(-?\d{4})-(\d{2})-(\d{2})$` を要求していた**ことに気づいた。month 精度の event 日付には表記が 2 つあり、

| 表記 | 件数 | フェーズ1〜5 の扱い |
|---|---|---|
| `YYYY-MM`（日を持たない） | **2464** | **全件が対象外** |
| `YYYY-MM-DD`（日はプレースホルダか実日付） | 1389 | 検査・訂正した |

**多数派は `YYYY-MM` のほう**だった。#33 のスイープも同じ正規表現なので、この 2464 件は
Issue 起票の時点から一度も検査されていない。内訳（フェーズ5 完了時点）:

    note に旧暦月なし        1094   照合の足場が無い（別タスク）
    換算済み                  433
    未換算候補・単一月        603   → 6a
    未換算候補・複数月        262   → 6b（記述順で決まる 232）/ 6c（決まらない 30）
    説明不能                   72   ISO 月が note のどの旧暦月とも一致しない（別タスク）

判定はフェーズ5 と同じ向きで行い、**864 フィールドを訂正**した（6a 603・6b 232・6c 29）。
6c の 30 件は 1 件ずつ note と原典で対応月を決め、**1 件だけ「換算してはいけない」と判定した**:

> `qing-xuantong.amnestyCount[1].date = 1934-03` — 満洲国康徳元年の即位・恩赦。
> 「大同三年三月一日，即皇帝位」の三月一日は**太陽暦**であって旧暦ではない。
> 清朝滅亡後のレコードに旧暦換算を当ててはいけない（変更した 864 件のうち 1900 年以降は
> `qing-xuantong` の宣統元年六月＝1909 年の 1 件だけで、これは清朝なので旧暦で正しい）。

干支での自己検証も掛け、25 件で note の干支が sxtwl の当該旧暦月に実在しなかった。
フェーズ5 で決めた方針どおり月ラベル基準で換算している（史書暦との朔・置閏の差）。

**検出器（両表記対応）での前後**: 2759 件中 **1016 件 → 156 件**が「note のどの旧暦月からも説明できない値」。
残る 156 件は #34 の未換算とは別種（例: `hou-han-shundi.rebellionSuppressionCount[12].startDate = 0140-05-01`
に対し note の旧暦月は正月だけ）。note が終了月しか書いていない場合と、値そのものが誤っている場合が混在する。
