# 名前まわりのスキーマ設計（Issue #37 単位2・単位3・2026-08-03）

Issue #37 の3つの作業単位のうち、**設計判断を待っていた単位2（元号フィールド）と
単位3（`name.ethnicName` への分離）**の設計。単位1（廟号・諡号の悉皆補充）は前提なしで
着手できるのでこの紙の対象外。

- 単位2 … **設計をする**（2026-08-03 ユーザー指示）。この紙が設計で、実装は別段
- 単位3 … **採用**（同）。形と検査をここで決め、32件の移行は別段
- `jin-taizu` の姓欠落 … **この turn でデータを直した**（4節）

作法は [V3_MIGRATION_PLAN.md](V3_MIGRATION_PLAN.md) と
[SCHEMA_CHANGE_CHECKLIST.md](../../data/schema/SCHEMA_CHANGE_CHECKLIST.md)（`R-CLAIM-GATED`）に従う。
**この紙は設計なので、チェックリストの対応表には行を足していない** — 実装が入る変更で、
ゲートの実体と同じコミットで足す（表に「名前だけあって実装が無いゲート」を置くと
`check_rules.py` が落ちる）。

## 1. 単位2 — 元号

### 1-1. 人物側に欄を作らない（改元 event から導出する）

**新しい主張は `events[].eraName` の1つだけ**で、「この皇帝の元号一覧」は
`reignSummary` と同じ**導出値**にする。人物側の欄を作ると、同じ事実に対して
主張が2つ・ゲートが2つになるが、片方は他方から計算できるので独立の主張ではない。

導出できることは実測で確かめた（2026-08-03）。

| 測ったこと | 結果 |
|---|---|
| `commonName` の括弧に元号帝を持つ35人（誤検出4人を含む）の元号名が、その人の `eraChangeCount[].events[]` の中にあるか | **31/31**（誤検出4人＝`元帝（孝元帝）` などの諡号を除く） |
| Issue #35 で検索から落ちた5件（義嘉・正平・天正・天成・天啓） | **5/5** 改元記事の中にある |
| 改元 event が0件の皇帝 | 33人。うち `commonName` に元号帝を持つ人は**0人**・清は0人 |

**素の文字列一致では4件が落ちる**（`ming-xuanzong` 宣徳／`ming-shenzong` 万暦／
`ming-xizong` 天啓／`qing-wenzong` 咸豊）。`commonName` が新字体、note の中の原文引用が
底本の字体（宣德・萬曆・天啟・咸豐）で、**同じ元号が別の文字列になっている**ためで、
`scripts/hanzi_norm.py` の `norm_for_match` を通すと4件とも一致する。
**この字体の食い違いこそが構造フィールドを立てる理由**で、いま書けるゲートが
散文の文字列一致では弱い、という Issue 本文の見立てはここでも当たっている。

### 1-2. 欄

改元 event（`eraChangeCount[].events[]`・**681件**）に足す。

| 欄 | 型 | 内容 |
|---|---|---|
| `eraName` | string | **この event が建てた元号の名**。日本語の新字体（「万暦」「天啓」）。表示に出る側 |
| `eraNameRaw` | string \| null | 同じ元号の**底本の字体**（「萬曆」「天啟」）。任意・遡及しない |

- **欄名を `eraName` にする理由**: 既存の `eraId` は中身が時代区分（`qin-han`・`yuan`）で
  年号ではない。`era` を人物側で再利用すると読み違えるので、**人物レコードには足さない**
  （1-1）ことで衝突そのものを避ける
- **`eraNameRaw` は `R-EVENT-DATE-RAW` と同じ作法**（原表記を同じ要素に残し、
  再演できる形にする）。日付の `*Raw` が「換算の再演」を可能にするのと同じく、
  ここでは**新字体への書き換えの再演**を可能にする
- **改元されて捨てられた側の元号は書かない**。`eraName` が指すのは新しく建てた元号1つ

### 1-3. 主張と検査

主張は「**この改元 event が建てた元号の名は `eraName` である**」。

| # | 検査 | 実装先 | 嘘なら落ちる条件 |
|---|---|---|---|
| A | 形 | `validate_emperors.py::check_era_names`（CI・コーパス不要） | 漢字2〜4字である／「元年」「改元」「建元」を含まない（記事の一節を丸ごと入れた形を弾く） |
| B | 新字体変換の再演 | 同上 | `eraNameRaw` があるとき `norm_for_match(eraName) == norm_for_match(eraNameRaw)`。**これが「表示の字体を勝手に作った」を落とす** |
| C | 同じ event の中に根拠がある | 同上 | `norm_for_match(eraName)` が同じ event の `note`（原文引用を含む）の正規化本文に部分文字列として在る。**実測で 31/31＋5/5 が通る**（1-1） |
| D | 底本に在る（強い側） | `verify_quotes.py::cmd_check_era_names`（ローカル専用・要コーパス） | `eraNameRaw`（無ければ `eraName`）が `source.page` の名乗る巻の底本に、**改元アンカー（`改元`／`建元`／`為◯◯元年`）と同じ行で**在る。2文字の断片は単独ではどこにでも当たるので、**アンカー同行を条件にしないと実在検査にならない** |

**検出力テスト** `tests/test_era_name.py`（実データに違反が無い欄では本番の「0 errors」は
証拠にならないので、合成レコードで発火を測る・チェックリスト手順4）:

1. `eraName` を1字差し替えると C が落ちる
2. `eraNameRaw` を別の元号にすると B が落ちる
3. 底本の別の行（改元アンカーの無い年次表記の行）にしか無い元号で D が落ちる
4. `eraName` に「改元康熙」を入れると A が落ちる

**C は note に依存する。** 年表4種の散文 note を内部側へ移す計画（RESIDUAL.md の
「年表4種の note を構造フィールドへ」）が動いたら、C の参照先は `note` から
その event の `quotes[]` へ移す。移すまでの間、**note を内部側へ移した event で C を
黙ってスキップさせない**こと（スキップは充足数を減らすのでラチェット E が落ちる）。

### 1-4. 移行とラチェット

**681件は一度に埋まらない。** 転記は原典を読む作業で `R-NO-AUTOGEN` の対象外（確定済み
結果の転記）だが、底本の字体を写す以上は `R-QUOTE-NO-TYPE`（ツール出力からのコピー）に従う。

- E: **ラチェット** — `eraName` を持つ改元 event の数が減ったら落ちる
  （`validate_emperors.py`。チェックリスト手順5）
- 残量は [RESIDUAL.md](../process/RESIDUAL.md) に行を足す。**母集団は681件**で、
  note に改元アンカー（`改元`／`建元`／`元年`）を含むものが **676件**＝転記の当たりが
  ほぼ全件に立っている。残り5件は note の書き方が別で、個別に読む
- **着手順の先頭は Issue #35 の5件**（義嘉・正平・天正・天成・天啓）。これだけは
  「検索から落ちたものの回収」という別の締切がある（1-5）

### 1-5. Issue #35 の5件の回収

`commonName` を政権名から人物名へ直したとき、括弧の中にしか無かった元号が
`searchTextOf` から落ちた。**`aliases` へ逃がすのは誤り**（個別ページで「別称」チップとして
出て名前の種類が合わない）ので、この欄で回収する。

サイト側は `searchTextOf` に**改元 event の `eraName` を足す**。表示（名前チップの「元号」行）は
いま明清29人だけが `commonName` の括弧から出しているが、`eraName` が入った皇帝から
順に増える（NAME_DISPLAY_PLAN 4節の「元号行が出るのは当面明清29人だけ」はこれで解ける）。

**「どの元号で呼ぶか」は編集判断としてサイト側に残す。** 明英宗（正統／天順）・
清太宗（天聰／崇徳）のように元号を2つ持つ皇帝がいて、導出で出るのは**集合**である。
呼称に使う1つを選ぶのは `display-name.ts` の上書き表の仕事で、データ側の主張ではない。

### 1-6. 決めていないこと

- **`eraName` を持つのは改元 event だけか**。前帝が建てた元号を在位中ずっと使った皇帝
  （改元 event 0件の33人）には元号名の置き場が無い。実測で「`commonName` に元号帝を持つ人は
  この33人に0人」なので**当面は要らない**が、単位1で元号の表示を全員に広げるなら再検討する
- **元号の期間（開始年・終了年）を持つか**。持たない。期間は改元 event の `date` から
  導出でき、`R-DATE-CLAIM-SCOPE`（深さそのものが主張）と衝突しない形にするには
  別の設計が要る。**元号の名前だけを主張する**

## 2. 単位3 — `name.ethnicName`

**採用**（2026-08-03 ユーザー決定）。形と検査をここで決める。

### 2-1. 形

```jsonc
"name": {
  "personalName": "耶律徳光",              // 漢字の諱（漢風名・漢名・漢字音写・漢字諱）
  "ethnicName": { "kind": "khitan", "value": "耶律堯骨" },
  ...
}
```

- `kind` は `meta.catalogs.ethnicNameKinds` の ID。**ラベルはカタログ側**（v3 の作法）
- 括弧つき **32件**（実測・2026-08-03）の内訳は **民族名31**（遼9・金9・元11・北元1・清1）と
  **改名1**（`shiguo-beihan-liuchong`）。Issue 本文の「遼10・元12」は数え方の食い違いで、
  合計32は一致する

### 2-2. 対応表 — 相手側の種類は `kind` から一意に決まる

**同じ括弧が別の現象を指している**（`耶律徳光` は契丹名とは別の漢風の諱、`忽必烈` は
同じ名前の漢字音写）ので、`ethnicName` だけでは相手側のラベルが決まらない。
**`kind` から1対1で決まる4行の表**にすることで、サイト側の政権別テーブル
（`display-name.ts` の `ETHNIC_NAME_LABEL`）を消せる。

| `kind` | ラベル | `value` の字種 | `personalName` の性格 | ラベル | 該当 |
|---|---|---|---|---|---|
| `khitan` | 契丹名 | 漢字 | **別の諱**（漢風名） | 漢風名 | 遼9 |
| `jurchen` | 女真名 | 漢字 | **別の諱**（漢名） | 漢名 | 金9 |
| `mongol` | モンゴル語名 | カナ | **同じ名前の漢字音写** | 漢字音写 | 元11・北元1 |
| `manchu` | 満洲語名 | カナ | 漢字の諱 | 諱 | 清1 |

これで個別ページの名前チップは**データだけで**組める:

```
遼 太宗   契丹名 耶律堯骨 ／ 漢風名 耶律徳光
金 世宗   女真名 烏禄 ／ 漢名 完顔雍
元 世祖   モンゴル語名 クビライ ／ 漢字音写 忽必烈
清 太宗   満洲語名 ホンタイジ ／ 諱 愛新覚羅皇太極
```

### 2-3. これは「欄を1つ足す」ではない — `personalName` が21件動く

**遼9件と元・北元12件の `personalName` の値そのものが変わる**（`耶律堯骨（耶律徳光）` →
`耶律徳光`、`クビライ（忽必烈）` → `忽必烈`）。金9・清1は括弧を落とすだけで前半が残る。

`personalName` は365人全員で h1 の脇に出る補助名の素材なので、**移行の影響は32件に閉じない**:

- **カードの補助名が変わる**。遼8件は現行のサイト側規則（`regimeId === "liao"` なら
  括弧の中）が不要になり**規則どおりに通る**＝上書きが減る。逆に**元・北元12件は
  「カードにはカナを出す」ため、`ethnicName` を出す規則が新たに要る**（政権別1行）
- **ふりがな**（`data/name-readings.json`）・**かな検索**（`kana-readings.ts` の `TABLE_SOURCE`）に
  `忽必烈`・`妥懽帖睦爾` などの漢字音写が新しい表示文字列として出る。`rubyOf` は
  未登録で throw するので、移行と同じ変更で足す（`R-COUPLING`）
- **`resolveQualifiedNameCollisions`** を通す（冠称形の一意性）

**32件は機械の一括置換にしない。** 括弧の前後を入れ替える形が政権ごとに違い、下の3件は
規則の外にある（2-5）。単位1と同じ「1件ずつ原典で確かめて転記」で進める。

### 2-4. 主張と検査

主張は「**この人物の `ethnicName.value` は `kind` の言語・民族の名である**」。

| # | 検査 | 実装先 | 嘘なら落ちる条件 |
|---|---|---|---|
| A | `kind` の実在 | `validate_emperors.py::check_ethnic_name` | `meta.catalogs.ethnicNameKinds` に在る |
| B | **`kind` と政権の整合** | 同上 | カタログ側の `regimes` と レコードの `regimeId` が一致する（`khitan` は遼・西遼のみ／`jurchen` は金のみ／`mongol` は元・北元のみ／`manchu` は清のみ）。**取り違えを落とす主力** |
| C | 字種の整合 | 同上 | `kind` ごとに `value` の字種を検査（`khitan`・`jurchen` は漢字のみ／`mongol`・`manchu` はカナのみ）。2-2 の表が壊れたら落ちる |
| D | 底本に在る | `verify_quotes.py::cmd_check_ethnic_names`（ローカル専用） | **漢字の側**がその人物の名乗る巻の底本に実在する。`khitan`・`jurchen` は `value` を、`mongol`・`manchu` は `personalName`（漢字音写・漢字諱）を照合する。**カナは底本に在り得ないので `kind` 単位で免除**し、そのことを明文にする |
| E | 移行のラチェット | `validate_emperors.py` | `personalName` に `（` を含むレコード数が増えたら落ちる（移行中は減る方向だけ許す）。完了後は0を強制 |

**D が効く理由**: 全4 kind で**必ず片側は漢字**なので、免除しても「どのレコードも
底本照合を1本は通る」が保てる。カナだけの主張が配布物に残らない。

**検出力テスト** `tests/test_ethnic_name.py`:

1. 元の皇帝に `kind: "jurchen"` を入れると B が落ちる（クビライに「女真名」が生える形）
2. `mongol` の `value` に漢字を入れると C が落ちる
3. 底本に無い漢字名で D が落ちる
4. `personalName` に括弧を戻すと E が落ちる

### 2-5. 規則で決めない3件（着手時に原典で判断する）

- **`liao-taizu`** … 遼史は「姓耶律氏，讳亿，字阿保机」で**阿保機は字**。`ethnicName`
  （契丹名）として受けるのか、`courtesyName` を別に立てるのかは遼史の読みの問題で、
  2-2 の表からは決まらない。**通用形は耶律阿保機**なのでサイトの上書きは残る
- **`shiguo-beihan-liuchong`** … `劉崇（劉旻）` は**改名**であって民族名ではない。
  `ethnicName` では受けられない。**`aliases` へ入れる**（`aliases` は「別名・異表記」で、
  のちに名乗った名はこの種類に合う）。**Issue #35 の元号を `aliases` へ逃がすのを
  却下した理由（元号は名前の種類が違う）はここには掛からない** — 別人の名前ではなく
  同一人物の別の諱だからで、混同しないこと
- **`qing-taizong`** … `愛新覚羅皇太極` の「愛新覚羅」は氏族名。データは原典どおりに置き、
  カードで落とすのは表示側の仕事（現行の `regimeId === "qing"` の規則のまま）

**民族名そのものが無い政権（西夏のタングート名・北魏の鮮卑名）は空のままにする。**
`ethnicName` が無いことは「調べていない」であって「無い」ではない。

### 2-6. `regnalTitle` は触らない

365人全員「皇帝」で情報量が無いが、収録基準そのものなので消さない（この設計の対象外）。
