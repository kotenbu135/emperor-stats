## 2. モーダル廃止（作業範囲は確定済み）

一覧のカードクリックで詳細ダイアログを開くのをやめ、そのまま `/emperors/[id]` へ遷移する。
`/database` の皇帝列とダッシュボードの `BarList` の行は**既に個別ページへ直リンク**なので、
これは「グリッドだけが例外だった状態を他の2面に揃える」変更。

### 実測: 戻り操作は対策不要

ダイアログが提供していた唯一の体験価値は「モバイルの戻るで一覧ごと離脱しない」ことだった
（`useDialogHistory` のコメント）。直接遷移にしたときの戻りを dev サーバーで実測した:

| 条件 | 遷移前 | 戻った後 | 判定 |
|---|---|---|---|
| 素の一覧・3000px | y=3000 / 365枚 | y=3000 / 365枚 | OK |
| 素の一覧・12000px | y=12000 / 365枚 | y=12000 / 365枚 | OK |
| `?dynasty=tang` | y=1012 / 24枚 | y=1012 / 24枚・クエリ保持 | OK |
| `?q=唐` | y=1500 / 38枚 | y=1500 / 38枚・入力欄に「唐」 | OK |

スクロール位置・絞り込み・検索語のいずれも復元される（Next.js のソフトナビゲーション＋
グリッド側の既存 URL 同期）。**スクロール復元の対策は要らない。**
※ これは dev（Turbopack）での実測。実装時に `out/` のビルド版で再確認する。

```
├─────────────────────────────────────────┤
│ ② 紹介文（Issue #16・200〜300字）             ← 新設 │
├─────────────────────────────────────────┤
│ ③ 基本情報（諱・廟号・諡号・在位）│ 回数系8指標      │
├─────────────────────────────────────────┤
│ ④ 即位の経緯          │ 死因の経緯（＋復位の経緯）  │
├─────────────────────────────────────────┤

│ ⑥ 関連動画 / 典拠・調査メモ（畳む）/ 前後ナビ       │
└─────────────────────────────────────────┘
```

- **幅は現状の `max-w-4xl`（1024px）を維持**。`/about` の読み物幅768px は使わない
  （数値の表と散文が同居する面なので、`/about` とは別の性格）
- 本文の級数は現状の14pxのまま。**紹介文だけ16px**（唯一の「読ませる」文）
- 節の見出しは h2。ヒーローの名前が h1（現状の `PageHeader` を置き換える）

### ヒーローの争点: 肖像なし221名（61%）

肖像は全144枚が 360×480 なので、**引き伸ばせる上限は200px前後**（現状は144px）。
肖像なしの人物で同じ枠にモノグラムを大きく置くと、ページ先頭の一等地が
「画像がありません」の告知になる。五胡十六国84%・南北朝80%が肖像なしなので、
**その時代のページはほぼ全部が弱いほうの見た目になる**。

→ 提案は**肖像がないときは枠ごと出さず、名前主導の組みに切り替える**（左右非対称を許容）。
判断は推論ではなく `tools/shots/` の実物（肖像あり1名・なし1名）で行う。
外部のデザイン系エージェントは入れない（2026-07-31 決定）。

### 回数系8指標の順位 — **数字だけ残す**（2026-08-01 ユーザー決定）

8件とも行き先が無いままリンクを外して数字だけ出す現状を維持する。全皇帝中の位置は
統計サイトの価値そのものなので、行き先が無いことを理由に落とさない。

**対象は回数系8指標だけ。** 生きているリンク2本は作り替えても残す:

- **在位期間の順位** → `/database?sort=reignApproxDays&order=desc`（旧 `/reign` の在位年数ランキング）
- **「のちに復位」**（`accessionSubNote`）→ `/database?reign=restoration`（旧 復位者一覧）

この2本は**個別ページからデータベースへ生き残っている唯一の導線**で、`/database` に URL 同期を
入れたのはこの着地点のためだった（SITE_DESIGN 2節）。解体のついでに消さないこと。
**新しいチャートは作らない**（recharts 2.15.4 固定＋Tremor だけという制約下で、
副次的なパネルのために図を1本起こすのは高い）。「上位10%」等の言い換えも入れない。

### 在位中の出来事 — **先頭20件＋残りを素の `<details>`**（2026-08-01 ユーザー決定）

中央値9件だが宋高宗223件・光緒帝116件・煬帝101件があり、20件以上が102名。
上位3名以外はほぼ全件がそのまま見え、長い人だけが畳まれる。

**Radix の `Accordion` は使わない**（`forceMount` を渡していないので閉じた本文が DOM から
消える＝静的HTMLから223件の日付付きテキストが落ちる）。素の `<details>` は閉じていても
DOM に残るので静的HTMLに全件出る。Issue #16 が検索での見え方を目的にしている以上ここは動かせない。

- **20件の境目は「種別フィルタで絞ったあと」の集合に対して数える。** 年表には種別ピル
  （改元・大赦・…）があり、223件を5件に絞った状態で元の集合を基準に分けると、
  `<details>` が空になったり「残り203件」の嘘の件数が出る
- **受け入れ確認は行数ではなく末尾のテキスト**でとる。宋高宗（223件）のページで、
  画面上いちばん最後に出る出来事の文字列が `out/emperors/<id>.html` に載っていることを確かめる
  （畳み方を間違えたときに落ちるのは末尾なので、`grep -c` の件数では検出できない）

## 5. Issue #16「各皇帝の紹介文」

> SEO対策として皇帝名でWeb検索をかけたときに皇帝の紹介文が検索結果に出るようにする。
> 一人ずつ作成する。他サイトからのコピペ禁止。

いまの `generateMetadata` は365ページとも同型の機械生成文（「◯◯の皇帝 ◯◯ の調査結果。在位…」）で、
人物ごとの内容差がほぼ無い。**紹介文はページ本文と `description`・JSON-LD の両方を差し替える**のが狙い。

### 格納先（提案: 別ファイル）

`data/emperor-profiles.json` を新設する。`data/emperors.json` に足さない理由:

- emperors.json は**正史原典から調査した事実**のデータセットで、`meta.status` で完了管理されている。
  紹介文は調査結果ではなく編集コンテンツで、性格が違う
- 約7MBのファイルを365回の追記で触ることになり、**並行セッションの read-modify-write と衝突**する
- 配布データ（CC BY 4.0）の中身が変わる。紹介文を配布物に含めるかは別の判断

### 分量

- **本文用 200〜300字**（ページの②）
- **`description` 用 1文・120字前後**（検索結果に出る長さ）
- この2つを別フィールドで持つ（本文の冒頭を切り出すと文が途中で切れる）

### 出典の扱い — **既存の調査結果の範囲内だけ**（2026-08-01 ユーザー決定）

紹介文に**調査結果の外の事実を足さない**。素材は `accessionRoute.note`・`deathCause.note`・
`reignSummary`・`reigns[].duration.source`・events・ages の note で、いずれも既に原典で
検証済みの内容。紹介文はそれを読者向けに言い直す作業であって、新しい事実を主張する作業ではない
（＝原典の再調査は発生しない）。

治績・人物像を本紀から新たに調べて足す案は**採らない**（採ると365人分に原典調査と同じ手順
＝コーパス参照・引用ゲートが要り、工数が桁で変わる）。「武帝といえば匈奴遠征」のような
一般に知られた事実であっても、調査データに無いものは書かない。

**罠**: 素材の note は調査時の原文ママ（`verify_quotes.py` の照合対象）で、中には正史の直接引用が
含まれる。紹介文へそのまま持ち出すと引用の取り扱い規約の対象になるので、**紹介文には
引用を持ち込まず地の文で書く**（引用を読ませたい場合は既存の「在位日付の典拠」節が担う）。

### 工程

365人を一度には書けない。**時代15区分のブロック単位**で進め、ページ側は
**紹介文フィールドが無くても成立する設計**にする（着手時点では365人中0人が空でないため）。

機械ゲート案（`scripts/validate_profiles.py`）: 文字数の上下限・全員分の重複 n-gram 検出・
人物名/王朝名/在位年が emperors.json と矛盾しないこと・空フィールドの検出。

## 6. 実装順序

1. **モーダル廃止**（2節）— 削除中心・範囲確定済み。先に入れると個別ページが唯一の詳細面になる
2. **個別ページ再構築**（3節）— 4節の論点が決まってから
3. **紹介文**（5節）— ページ側にフィールドを受ける口を作ってから、ブロック単位で執筆

1と2の間で `npm run build` ＋ `tools/capture-site.mjs` を通し、
肖像あり／なしの個別ページを実物で見て判断する。
