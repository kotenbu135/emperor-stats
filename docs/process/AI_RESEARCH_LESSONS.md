# 史書をAIで調査する方法の知見集

中国皇帝364人×12項目のデータセット構築（2026-07-15〜18、調査エージェント延べ数百体）を通じて得られた、**AI（LLMエージェント）で史書を大規模調査するための一般化可能な知見**をまとめる。

- 「何をするか」の作業手順は [RESEARCH_PROCESS.md](RESEARCH_PROCESS.md)、史料ごとの具体的マッピングは [CORPUS_NOTES.md](CORPUS_NOTES.md)、絶対的な制約は [CONSTRAINTS.md](CONSTRAINTS.md) を参照。本書は「なぜその方法に落ち着いたか・何が失敗したか」の記録であり、同種のプロジェクト（史料ベースの悉皆調査全般）を再び行う際の設計指針として読む。

## 1. 情報源の信頼性 — AIの要約を判定根拠にしない

**LLMは「もっともらしい要約」を作るのが得意なため、要約を判定根拠にすると誤りが混入しても気づけない。** 判定は必ず原典の該当箇所（本紀・列伝の原文）まで降りて行う。

- **WebSearch のスニペットだけで判定しない。** スニペットが史書原文を直接引用しているか、学術的信頼性のあるソース（維基百科・百度百科の原典引用部分、研究者のページ等）かを確認する。個人ブログ・まとめサイトのみが根拠の場合は confidence を下げるか原典に当たり直す（更始帝の死因調査でユーザー指摘を受けて確立した方針）。
- **AI翻訳サイト・解説サイトは「目次」として使う。** 二十四史のAI和訳サイト（aki-asahi.com）は該当人物・巻の当たりをつけるのに有用だが、AI翻訳自体を確定根拠にはしない。必ず原文で裏取りする。
- **史書自体のバイアスを織り込む。** 易姓革命後に編纂された正史は前王朝最後の皇帝を実際以上に悪く描く傾向が知られている。原典の記述をベースにしつつ、現代の学術的通説と食い違う場合は「諸説あり」として両論併記する。
- **「不明」を正式な調査結果として扱う。** 無理に一つの答えを決めず「不詳」「諸説あり」を用意する。さらに悉皆調査では**「調査済みだが不明」（空値＋note）と「未調査」（フィールド省略）を構造上区別する**ことが重要 — この区別がないと「調査漏れ」と「調べたが史料に記載がない」が混ざり、進捗管理も完了検証もできなくなる。五胡十六国・南北朝の傀儡皇帝や極短命の簒奪者では「生年不明が正しい調査結果」であることが多く、76人中44人が「調査済みだが不明」で確定したブロックもあった。
- **候補人物リスト自体の抜け漏れも疑う。** 「364人全員完了」は候補リスト内の悉皆性であり、候補リスト自体が完全である保証にはならない。実際、通史年表の設計検討で在位年カバレッジを機械集計（`reigns[].startYear`〜`endYear`の年ごとの在位人数）したところ905-906年が皇帝不在期間として現れ、唐哀帝（李柷）の収録漏れが判明した（唐は殤帝・李裕等の短命帝まで収録済みだったのに哀帝だけ欠落。2026-07-20発見）。この種の「連続性の破れ」を機械的に検出する手法（年ごとの在位人数カバレッジ集計、王朝ブロックの先頭/末尾皇帝の在位終了年と次王朝の開始年の突き合わせ等）は、候補リストの抜け漏れを見つける有効な監査手段になる。
- **旧暦→新暦換算（`sxtwl`）には日単位で1日程度のブレが生じ得る。** 同一人物・近接する日付でも、既存レコードとの突き合わせで新規換算が1日ズレるケースがあった（唐哀帝の崩御日「天祐五年二月二十一日」を`sxtwl`換算した日と、`資治通鑑`の干支表記「癸亥」から逆算した日が1日食い違った）。原典に直接の日次記載（「◯月◯日」）がある場合はそれを優先して換算し、干支のみのクロスチェックで1日程度の差が出ても無理に一致させようとせず、`verification.notes`に差異を記録した上で直接記載側を採用する。近接する既存レコード（例: 別人物だが同時期の即位/崩御日）との整合確認は、換算ミスの発見に有効。

## 2. 史料はローカルに置く — 外部サイトを叩かない

**数百人分の調査で外部サイトを都度取得するのは、効率面でも礼儀面でも破綻する。** 整理済みのオープンデータを1回だけ `git clone` してローカル参照するのが正解だった。

- 当初 ctext.org を都度 WebFetch していたが、Bot判定・アクセス制限のリスクがあり2026-07-16に全面廃止。GitHub公開のコーパス2種（china-history＝二十四史HTML、daizhigev20＝殆知閣テキスト）をローカルに取得し、以後の原文確認は「ローカルコーパス → だめなら維基文庫」の2段構えにした。
- **外部APIへの一括リクエストは「小規模検証 → 想定件数を提示して明示的許可 → 本実行」を必ず踏む。** 肖像画調査で Wikimedia API に364件を並列で投げて 429 と乱用警告を受けた失敗がある。429 が出たらリトライ・バックオフで粘らず即停止して方針自体を相談する。可能なら公式の一括ダンプ（オフライン処理）を優先する。

ローカルコーパスには固有の罠がある（詳細は [CORPUS_NOTES.md](CORPUS_NOTES.md)）。一般化すると：

- **ファイル名・ラベルを信用しない。** 列伝ディレクトリの巻数が絶対巻数でなく相対番号の書がある（宋史・金史・明史）。「原文」ラベルなのに中身が白話訳（現代語訳）というデータ不備もある（晋書の一巻で実例）。新しい書に着手する際は必ず1〜2件を原文の「卷○○」見出しと照合し、文体（文言文か現代語調か）を目視確認してからエージェントに配る。
- **OCR/転記由来の誤字がありうる**前提で、直接引用は文脈と照合する。避諱表記・PUA文字・人物記事の巻をまたぐ分散（朱友珪など）も個別に発生する。
- **発見した罠はブロックごとのメモに散在させず、1つのチェックリストに集約する。** 同種の罠を次のブロックでゼロから再発見するコストが実際に発生していた。

### 前処理の3段活用（コンテキスト効率の土台）

1. **行番号インデックス**: 章分割のない大容量ファイル（清史稿.txt 15.6MB等）は、本紀見出しを `grep -n` で洗い出して皇帝ごとの行範囲表を作り、エージェントには該当行範囲だけを Read の offset/limit で渡す。原文自体は全文読めるため精度は落ちない。
2. **人物ごとの原文キャッシュ（`_corpus_cache/<id>.txt`）**: 調査項目が複数グループに分かれていると、同じ人物の同じ本紀を最大4回読み直す無駄が発生する。コーパスから人物ごとの原文を**機械的に抽出するだけ**（判定は一切しない）のスクリプトで事前にキャッシュ化する。当初は「もう読み直さないブロックには不要」と選別していたが、「調査項目は後から増える」という理由で全ブロック標準運用に転換した — **悉皆調査では『この史料はもう読まない』という予測は当てにならない**。
3. **インデックス自体を実地検証する**: 行番号表の1エントリが誤っていた実例がある（清史稿の宣統本紀の終了行が志の途中を指していた）。表を作ったら代表箇所を `grep -n` で再検証してから使う。

## 3. 判定の設計 — 何をAIに任せ、何を機械化するか

**原則: 史実の判定はAIエージェントの個別調査、構造検証・転記・集計はスクリプト。** この線引きが最重要で、逆転させると両方失敗する。

- **判定のスクリプト化（データの自動生成）は禁止。** このプロジェクトでは過去2回失敗している。人物ごとに1エージェントが原文を読んで判定する方式が最終的に364人×12項目を通してエラー率ほぼゼロで完走した。
- **数え方の基準は着手前に文書化してユーザー承認を得る。** 「親征1回とは何か」「反乱と統一戦争の境界はどこか」のような基準は、調査中に必ず境界事例が出る。事前基準＋境界事例の都度ルール化（例: 簒奪前の挙兵は即位経路の領域として反乱に数えない、対立政権間の戦争は簒奪側と被簒奪側で非対称に計上する、宋遼西夏金は相互に外国関係として扱う）を基準文書に追記し続けることで、後続ブロックの判定が安定する。
- **基準を変えたら過去分を遡及監査する。** 被反乱回数の算入基準を途中で訂正した際は、訂正前に調査済みだった35名を監査して整合させた。
- **調査単位は項目の性質で選ぶ。** 
  - 皇帝個人の行為（改元・親征等）→ 人物ごと1エージェントの本紀通読。
  - 王朝単位の離散イベント（遷都）→ 王朝単位でイベント年表を先に確定し、在位期間へスクリプトで逆引き割当（364エージェント→30エージェントに削減）。ただし逆引きには同名別政権の衝突・皇帝号採用前のイベント・対立皇帝の並立など機械照合で解けないケースが残るため、「自動マッチ → 曖昧なものは note を読んで手動オーバーライド → 構造的グレーゾーンは既存の例外規定を類推適用」の3段構えにする。
  - 既存調査の副産物が使える項目（年齢）→ 新規の原典探索より先に、既に支払い済みの調査コスト（死因・即位経路調査の note・出典ページ）の再確認を起点にする。
- **同じ原文を読む複数項目は1エージェントに合算する（合算パス）。** グループ3（親征等）とグループ5（年齢）を合算した結果、7ブロック・188名を通して精度劣化なし・機械検証エラーほぼゼロで完走した。ただし導入時は**明示的なロールバック条件**（見落とし増加・検証エラー率悪化・削減効果僅少）を決めた試験導入とし、ブロックごとに条件該当の有無を記録して継続判断した。
- **旧暦→太陽暦換算は「日番号と干支の二重記載」「在位中崩御なら reigns.endDate」との突合で必ず裏取りする。** ages 日付の ISO 正規化（2026-07-21、62件）では、干支と日番号の両方が原文にある日付は sxtwl 換算で両者の一致を確認し、在位中崩御の 17 件はフェーズB検証済みの endDate と完全一致することを機械 assert した。この突合で、原文転記時の干支誤記 2 件（後唐荘宗の生日「癸亥」→sxtwl では 22 日=癸酉、崩御「丁丑」→四月朔は丁亥）を検出できた。また **4 世紀（東晋期）の日付は sxtwl（定朔ベース）と当時の官暦（平朔）の朔差で干支が旧暦月内に見つからないことがある**（姚興の「二月丁未」・石遵の「十一月丙辰」で発生）。この場合は日精度をでっち上げず月精度に落とし、旧暦月の太陽暦多数月を採用する。旧暦月だけ判明している日付の月精度換算も同じく多数月方式（例: 旧暦九月→大半が重なる 10 月）で統一する。 出典QAフェーズBブロック1で `reigns[].endDate` を訂正した際、同じ崩御日を持つ `ages.deathDate`（4件）と note 内の日付引用（2件）の同期を取りこぼし、公開サイトの JSON-LD に旧値が出たままライブ検証まで気づけなかった。訂正対象のフィールド名だけ直すのではなく、旧値の文字列でレコード全体（および表記規約が同じはずの隣接フィールド）を grep して残存参照を列挙するのを訂正手順の定型に含める。
- **BCE の年は「規約」を先に固定してから換算する（2026-07-22、前漢105件の年規約統一の教訓）。** 紀元前の日付は「歴史年直記（前n年→-n）」と「ISO/天文年（前n年→-(n-1)）」の2規約があり、入力者ごとに混在すると1年ズレが大量発生する（前漢では BCE イベント127件中105件が旧規約だった）。さらに漢初（太初改暦・前104年より前）は年始が冬十月のため、冬十月〜十二月・閏九月のイベントは紀年の対応年より1年前のユリウス年に落ちる — この年またぎと規約ズレは打ち消し合って「たまたま正しい値」を作ることがあり（例: 文帝元年冬十月＝`-0179-10`）、目視では発見できない。規約はスキーマ文書に明文化し、note に「前n年」を併記して CI で date と機械突合する。また **sxtwl の干支「日」の特定は60日周期のため暦法に依存せず頑健だが、旧暦「月」のラベル（何月か）は漢代太初暦の月境界を再現する保証がない** — 干支から日精度を確定するときは通説の換算日と交差検証し、一致しない場合は月精度に留める。

## 4. 並列エージェント運用 — 構造化と検証

数十体の並列エージェントから返る結果を人手で扱うと、転記ミスと目視コストで破綻する。**「LLMの出力をLLMが書き写す」工程をゼロにする**のが設計目標。

- **構造化出力（schema強制）を必ず使う。** 自由文JSONを手で heredoc に書き写すのは、漢文引用を含む長文の再入力であり改変・脱字リスクがある（実際に一度やってしまい、以後禁止した）。
- **id はプロンプトでピン留めする。** エージェントは人物名から勝手にIDスラッグを自己生成しがち（あるブロックでは35名中20件超が不一致）。「返すJSONの `id` は指定した `<id>` を一字一句そのまま使うこと。独自生成禁止」という文言と、プロンプト本文への id 直接埋め込みで、以後のブロックは不一致ほぼ0件になった。
- **マージスクリプトに機械検証を内蔵する。** `count == events.length` の一致、スキーマ外キーのホワイトリスト除去、id照合をスクリプトが自動チェックし、不一致ならエラー終了。毎回の目視チェックを廃止できた上、実際に count 更新忘れ等の軽微ミスを複数ブロックで機械検出した。
- **マージは journal（エージェントの構造化出力の生記録）から直接組み立てる。** メイン会話に表示された要約からではなく、実行記録ファイルをスクリプトで読む。表示は「人物ごとのカウント表＋エラー有無」の要約のみで、保存データの粒度は落とさない。
- **完了宣言の前に必ず悉皆実測する。** チェックリスト上は「364人完了」でも、jq でフィールド保有数を実測したら355人しかいなかった事例がある。原因は、合算パスで後からデータセットに追加されたブロックが、既に完了扱いだった別グループのチェックリストに遡及追加されていなかったこと。**チェックリストは自己申告であり、完了判定は常にデータ本体の機械計測で裏取りする。** 累計値も「前回累計＋今回人数」の単純加算は重複分を二重計上する（実際に誤った）ため、毎回実測する。

## 5. コンテキスト・トークン効率 — メイン会話は司令塔に徹する

全34セッションの実測（Langfuse集計）で、トークン消費の96.6%は cache_read（毎ターンの文脈再送）であり、モデルの生成量は1%未満だった。つまり**コストはほぼ「メイン会話にどれだけ文脈を積んだか×残りターン数」で決まる**。ここから導かれる設計：

- **メイン会話で大きなファイルを Read しない。** データ本体（約7MB）は jq/python 経由で必要部分のみ抽出。**Workflow の中間結果ファイルも同じ扱い**（本体には適用していたのに中間結果で適用し忘れ、900行超をメイン会話に載せた失敗がある）。
- **セッション序盤の大出力は複利で効く。** あるターンで載せた文脈はその後の全ターンで再送され続けるため、冒頭20〜30ターンでの大きな Read/Bash 出力が最も高くつく。検証スクリプトの出力は「一致件数＋不一致行のみ」を基本形にする（全一致行を print して24KBのツール出力になった失敗がある）。
- **エージェントへの入力は「メイン会話でしか用意できない情報」に絞る。** 既存レコードを args に埋め込むと構築だけで32KBをメイン会話が負担した。代わりに「各エージェント自身が jq で自分のレコードを取得する」方式（args には史料マッピングだけ渡す）にする。その際 jq は**必要フィールドだけの射影**にするとエージェント側の読み込みも減る。
- **依存関係のない独立なツール呼び出しは1レスポンスに束ねて並列発行する。** 全34セッションの実測で並列化率は0.2%に留まっていた。逐次「1呼び出し＝1ターン」は cache_read の複利をそのぶん増やすため、独立な Read・Bash・エージェント起動はまとめて発行する。
- **本体調査は Workflow 1回に集約し、メイン会話は検証・マージのみ行う。** サブエージェントの cache_read はメイン会話に合算されないため、ターン数の複利を回避できる。最も軽かったセッションはこの構成（メイン会話の Read は3件のみ）だった。関連ファイルの読み込みも `cat a; echo ---; cat b` で1コマンド化するとターン数が減る。
- **失敗エージェントの再実行は「対象を絞った小さい新規Workflow」が安全。** resumeFromRunId は「同じ script+args ならキャッシュヒット」のはずだが、実際には16人×3回のフルリランが起きた実例（推定9.5Mトークンの無駄）や、配列先頭の変更で全再実行された実例がある。resume 後はエージェント実行数が想定と一致するか確認する。1〜2名の修正なら単発の小Workflowで済ませる。
- **「複数人物をまとめて1エージェントに長時間任せる」は人物分割より高くつく。** 出典マッピング調査を単発エージェントに任せたところ、1体で8.5Mトークン（69ターン）を消費し全237体中最大だった。15人を超えるようなまとめタスクは人物単位の並列Workflowに分割する。

## 6. 記録の運用 — 状態を1か所に、知見は都度その場で

- **進捗はチェックリスト（ドキュメント）とデータ本体のメタ情報を同じタイミングで更新する。** 片方だけ更新すると次のセッションが古い前提で動く。ブロック完了ごとに「データ反映・メタ追記・チェックボックス・特記事項の記録」をワンセットで行う。
- **実務知見はリポジトリのドキュメントに残す。** セッション用メモリはマシン間で共有されず、他の作業者（人間・AI とも）から見えない。史料マッピング・罠のチェックリストのような再利用情報は必ずリポジトリ側（本 docs/）に書き、メモリはそのポインタと経緯の記録にする。
- **判断根拠をデータに残す。** 境界事例の判定は結論だけでなく理由を各レコードの note に書く。後から基準を再検討するとき、監査するとき、サイトで「なぜこの数え方か」を説明するときの全てに効く。

## 7. 結果（この方法で達成できたこと）

### 8-2. 検証器の緩さは、欠陥そのものより長く生き残る（2026-08-02 全件再照合の教訓）

上の全件検証から10日後、同じ6,847件を**基準を上げて**測り直したところ、
**252件が「底本で確認できない」ものとして新たに浮かんだ**。データは1件も変わっていない。
変わったのは検証器だけである。

- **緩いしきい値は、それを必要にした別の欠陥を隠す。** 旧実装は断片を句読点を無視して10字で切っており、
  原文に無い並び（「…冬十月**戊辰帝崩**于…」）が断片になっていた。これでは当たらないので
  「断片の**半数**が当たれば合格」で吸収していた。**断片化の粗さとしきい値の緩さは対で発生し、
  対で直す**（片方だけ直すと大量に落ちる）。
- **「一度全件検証した」は基準込みでしか意味を持たない。** 記録には必ず合格条件を書く。
  「6,504件を検証済み」ではなく「半数断片一致で6,504件」と書いてあれば、10日後に読み直せた。
- **捨てている情報を探す。** `rg --json` は行番号をその場で返していたのに、台帳は書名しか記録して
  いなかった。再調査のたびに原文を探し直していたのは、取得済みの情報を捨てていたからである。
- **出典が複数当たるときの採用順を決めておく。** 順序が無いと「最初に見つかった1本」になり、
  本紀があるのに類書・**白話訳**を典拠に掲げる。順位付け（キャッシュ→正史→編年→載記→類書、
  白話訳は最下位）を入れるだけで、白話訳参照33件→0件・類書参照272件→25件になった。
- **既知の残件と新規の混入を分ける印を持つ。** 未解決を全部エラーにすると運用が止まり、
  全部警告にすると新規混入が埋もれる。`--triage` で印を付け、**印の無い未解決だけをエラー**にする。

### 8-2-1. 検出力テストは道具の穴を「仕様」として固定する（2026-08-10 名前欄の字体の教訓）

`hanzi_norm` の新字体差分表に `寛`↔`寬` が無く、新字体で書いた諡が底本の `宽` に当たらない
という穴があった。回避として明の2件だけ繁体で保存していたが、**その回避が
`test_posthumous_name_full.py` に「差分表に無い `寛` を使うと当たらない」という
OK ケースとして書かれていた**。表に2字を足して穴を塞いだ瞬間、そのテストが落ちた。

- **穴を回避した記録は、穴を塞ぐときの障害物になる。** 回避策をテストへ書くなら、
  「いまはこう振る舞う」ではなく**「塞いだらここを裏返す」**と書き添える。
- **道具を直したら `scripts/test_*.py` を全部回す。** データのゲート（validate・verify・check 系）は
  全部緑のままで、落ちたのは検出力テストだけだった。
- **ワークフローの `paths` に、そのワークフローが実行するファイルを全部入れる。**
  `scripts/test_*.py` が `paths` に無かったため、**テストだけを直したコミットで CI が走らず、
  直前の失敗が main に赤のまま残った**（2026-08-06 に `profile_prose.py` で踏んだのと同じ穴）。
- **穴の向きを見る。** 正規化表の欠落は「当たらない側」に倒れる — 正しい値が「底本に無い」と
  判定されるので、**値のほうを底本の字体へ寄せる圧力**が生まれ、同じ欄の中で字体が割れていく。

### 8-2-2. 走査の語は、書の途中で制度ごと変わる（2026-08-10 宋史の加諡の教訓）

「諡の段が本紀の外に在るか」を測る `sweep_posthumous_range.py` は諡に触れる9語で走査していた。
宋史へ流すと本紀の外の候補は53件で、そこに北宋の仁宗・英宗・神宗の加諡は**1件も出なかった**。
候補の隣の行を読んで初めて分かったのは、**宋は元豊六年に制度ごと改称していて**
（礼志「改加上尊謚作奉上徽號」）、以後の加諡を全部「徽号」と書くということだった。

- **語の一覧は「その書のその時期の制度名」であって、書の名前では決まらない。**
  同じ1冊の中で、ある年を境に語が入れ替わる。書ごとに語が違う（後漢書＝庙曰／宋史＝廟號）、
  1冊の中で語が割れる（魏書＝庙号・庙称・庙曰）に続く**3つ目の割れ方**。
- **語で当てる走査は、廟号や人名が語の間に入ると落ちる。** 宋史の書式は
  「加上〈廟号〉謚曰〈諡〉皇帝」で、2人並ぶ条の2人目は「，〈廟号〉曰〈諡〉皇帝」と語を持たない。
  同日の別の作業で本紀を「加謚」「加上尊謚」の2語だけで走査し、**「3人の加諡の条は本紀に無い」
  という誤った記録を残していた**（実際は3人とも本紀に在る）。
- **走査が「0件」を返したときこそ、候補の周りを人が読む。** 0件は「無い」と「語が違う」の
  どちらでも同じ顔をする。今回は候補として出た行の前後20行を読んで語の入れ替わりに気づいた。
- **道具を直したら、その道具で出した過去の結論を引き直す。** 語を足して舊唐書・明史・清史稿を
  流し直し、増えた候補（唐1・明6・清4）が全部太后の徽号と人名の誤当たりであることを確かめて、
  3書の結論が動かないことを示してから宋史の結論を書いた。

### 8-3. 「どれが異常か」は字形でも全体頻度でもなく、その資料と突き合わせて決まる（2026-08-02 字体混入684字の教訓）

引用に混入した日本語新字体を数えるのに、母集団の出し方を4回変えて4つの答えが出た。

| 数え方 | 件数 | 何が壊れているか |
|---|---:|---|
| 変換表のキーを含む | 2,983 | 将・国・号・乱・万・与は**簡体字と同形**。表は「新字体の一覧」であって「異常の一覧」ではない |
| 日本固有の字形を含む | 1,305 | `為` 761件は繁体の正字。**表の写像先が正しいとは限らない** |
| 底本のどこにも存在しない字形 | 50 | `広` は史藏に1回、`廃` は3回だけ現れる（別の書の異体・OCR ノイズ）ので網からこぼれる |
| **その引用が引いている底本と突き合わせる** | **684字**（431フィールド・181人） | 採用 |

- **辞書・表・全体統計は「異常かどうか」を決められない。** 決められるのは、その1件が
  実際に依拠している資料だけである。ここでは断片ごとに変換表から1字ずつ外し、
  外すと当たらなくなる字＝混入、と特定した（**アブレーション**）。
  `為`・`国`・`号`・`将` はこれで全て消えた（＝底本に実在する＝版差であって混入ではない）。
- **数えた対象が「引用」なのか「フィールド全体」なのかで桁が変わる。** 最初の70件には
  note の**日本語の地の文**（「事実」「見込み」）が入っていた。母集団の定義を先に書く。
- **ゲートは変換表ではなく底本を基準に書く。** 「表に載っている字を含むか」ではなく
  「**表の助けなしに底本へ当たるか**」。表の網羅性に一切依存せず、想定外の字も止まる。
- **逃げ道は1本だけ用意し、理由を書かせる。** 底本のほうが壊れている実例が2件あった
  （北史が「糖**追**」と化けている／魏書から `䴥` が落ちている）。逃げ道が無いゲートは、
  正しい引用を落とすか、最初にぶつかった人に無効化されるかのどちらかになる。
- **機械照合の結果は決定的にする。** 候補の並び順を検索器（rg）の返す順に任せていたため、
  同じ引用が実行ごとに別の書へ解決したり未解決へ落ちたりしていた。並べ替えの鍵に
  パス名を足すまで、「直したから落ちた」のか「たまたま落ちた」のか切り分けられなかった。

### 8-4. 散文は witness にならない — 突き合わせる相手が「主張」か「作業ログ」かを先に決める（2026-08-02 Issue #40 ゲート実装の教訓）

「note の日付・年・年齢を実フィールドと突合する」「note の続柄語を軸・系譜エッジと突合する」という
2本のゲート案を実装し、**どちらも測定で否定された**。設計時にはどちらも自明に見えていた。

| 案 | 母集団 | 不一致 | 実欠陥 |
|---|---:|---:|---|
| conversion の ISO 日付 vs 在位日付 | 306 | 10 | ほぼ0 |
| 欄名に隣接する ISO 日付 vs その欄 | 153 | 21 | ほぼ0 |
| 年齢語（享年・数え N 歳）vs `ages` | 260 | 57 | 0 |
| `accessionRoute.note` の続柄語 vs 軸 | 354 | — | 先代を指すのは2割未満 |
| 先代の名前でアンカーした続柄語 vs 軸 | 59 | 8 | 0 |

- **調査 note は「作業ログ」であって、欄の値の主張ではない。** 主用途は
  「現行 X → Y に訂正した」「既存 X は2ヶ月遅かった」という**捨てた側の値の記録**なので、
  素朴に突き合わせると**訂正前の値を現在の主張として読む**。突合の向きが反転する。
- **散文は欄を名指ししていない。** 「即位時年齢は数え16歳」を `deathAge` の主張として拾う。
  「孫権」「公孫帝」「中黄門孫程」の `孫` を続柄語として拾う。
  「文宣帝の実弟」は正しいが、**先代は文宣帝ではなくその子**なので軸とは食い違って見える。
  否定（「桓帝は子がなく」「実子ではなく養子」）と連鎖（「李雄の兄李蕩の子」）も同じだけ出る。
- **witness は構造フィールドか別のエッジに置く。** 同じ目的の検査でも、散文を読まずに
  `relationToPredecessor` と血縁エッジの実体（「子」なら先代が親エッジに実在するか）を
  突き合わせる形にすると、216件を判定して誤検出0で回る。
- **ゲート設計の表には「何と何を突き合わせるか」だけでなく「その相手は主張か」を書く。**
  この2本が転んだのは、突き合わせる対象の**性格**を書かずに対象の**名前**だけで設計したから。
- 副産物として、宣言の形をとる部分だけは突合できた（「〜は null とした」55件中3件が陳腐化・
  「欄名 旧→新」の右辺5件）。**主張として書かれた文だけがゲートに使える。**

### 8-5. 検出器が「Xと名乗っている」と言うとき、Xをどこから読んだかで結果の大半が決まる（2026-08-02 Issue #40 G1 のトリアージ）

「note が名乗る書に引用が無い」99件を原典に当て直したところ、**書名そのものの誤りは3割弱**で、
残りは検出器・正規化・引用の作り方の側の欠陥だった。件数を減らした4つの修正はどれも
「何を名乗りとして読むか」に関わる。

- **漢字だけへ潰してから隣接を見ると、書名の並記が消える。** 『魏書』『北史』とも、は
  正規化後に「魏书北史」と地続きになり、「三国志魏書を2書に割らない」ためのロジックが
  後ろの北史を落とす。99件のうち27件がこれだった。漢字以外を**長さを保つ区切り**へ潰す。
- **名乗りは散文だけでなく構造フィールドから採る。** note が書名を書かずに引用し、
  `source.page` にだけ「十国春秋 巻五十八」と書く形が十国春秋・旧五代史で頻出する。
  note・`source.page`・`conversion` 本文の和集合にすると、**照合対象が 2,527 → 3,687 件**に増えて
  （＝「書名を名乗っていない」と諦めていた1,400件が判定可能になった）失敗はほぼ横ばいだった。
  母集団を増やして失敗が増えないなら、それは検出器の適用範囲が広がったということ。
- **正規化の写し先が異体字だと、そこで止まる。** 新字体表が「衛→衞」「併→倂」と異体字側へ
  写しており、opencc t2s は衞・倂を知らないので簡体コーパスの「卫」「并」に永久に当たらない。
  **未解決引用（Issue #38）の生成源**でもあり、向きを逆にして 234 → 217 件に減った。
  字体ゲート（`norm_strict`）でも同じ表を当てる——引用が「衞」と書くのは新字体の混入ではない。
- **母集団から落として件数が減るのを、精度が上がったと読まない。** 断片が「年号＋月＋干支」だけの
  日付表現（`光大二年十一月甲寅`）は原文の一続きの句でないことが多いが、**213件のうち173件は
  名乗る書にそのまま在って合格していた**。落とすと消えるのは失敗40件だけで、そこに書名誤りが
  紛れていても見えなくなる。判定はそのまま行い、**報告を別のバケツに分ける**。

`bookAllow`（理由必須の許可リスト）に落ち着いた件の過半は、**コーパスの一書の中で1箇所だけ字が壊れている**型だった:
周書ファイルは蕭詧の「詧」を全篇「察」に置換（「外示助察備禦」が非文になる）、晋書は天文志の1箇所だけ
「慕容ＪＩ」と全角ラテンに化ける、明史は「讨平」を「讨症」、新五代史は「廣政」を「庆政」、
陸游南唐書は「己卯」を「已卯」（干支として成立しない）、魏書は文成帝の諱を全篇「浚」で通す。
**同じ書の他の箇所と比べれば機械でも見分けがつく**（明史の同巻には「山云讨平柳、浔蛮」がある）。

残りは**引用の切り出しが原文の非連続を連結している**型で、書名の問題として現れるが原因は別:
`「齊献武王（高歡）」` と括弧の補足を鉤括弧の内側に入れて断片が「齊献武王高歡」になる、
`「冬十月丙寅、车驾还宫」` と離れた2箇所を繋ぐ（底本は間に「癸亥，曲赦徐州。」が入る）、
`「（康熙六十一年十一月）甲午…」` と本紀本文に一度も出ない元号名を補う。
**切り直すときは連続する漢字が6字以上残る形にする**——断片は5字未満の節を捨てるので、
短く切り直すとゲートの検査対象から外れてしまう。

## 9. 元号日付の暦換算 — 換算の自己検証を系統誤りの検出器にする（2026-07-22 events 日付 ISO 正規化の教訓）

events 約1,000件の日付正規化で、機械換算の不一致から約25件の年・月・干支の取り違えを検出・訂正した。

- **元号→西暦の対応付けは系統誤りが混入しやすい。** 実例: 宋史仁宗紀の bare な年見出し（「二年春」等）の
  取り違えで年が1〜2年ズレる（安化州蠻の乱は3年ズレ）、遼・乾統の起点を1111年と誤算して+10年、
  南漢・大宝の起点誤算で+1年。元号表記のままの日付は必ず sxtwl 換算＋自己検証を通す。
- **自己検証の型**: (1) 干支は当該旧暦月内に一意に存在すること（不在なら日付をでっち上げず月精度へ格下げ）、
  (2)「朔」は1日一致（史書朔と天文朔の1日差＝進朔は干支日を採用し note 明記）、(3) 年注記・在位範囲との突合、
  (4) 周辺記事の朔干支アンカー（「三月壬辰朔」等）で年を一意に確定できる。
- **旧暦十一月・十二月は年またぎする。** ISO 年は必ず sxtwl の太陽暦出力から取る（年注記は紀年ラベル年）。
  武周の周正（載初元年正月＝建子月）のような改暦も sxtwl が月番号でモデル化している。
- **sxtwl と史書の月ラベルがまとまってズレる時代がある**（5世紀北魏〔玄始暦〕・隋・前蜀など、閏月配置差）。
  ズレた月の干支は隣接月に实在しても採用せず、記事順・朔アンカーで日を一意にピン留めできる場合のみ日精度、
  できなければ月精度（先例: 姚興・石遵・北魏宣武帝・南斉明帝）。
- **precision 欄の自由記述は情報の墓場になる。** 「day（干支のみ：○○、未換算）」型のトークンに元号日付が
  700件近く埋もれていた。日付情報はフィールド（date）に構造化し、precision は year/month/day/null に固定する
  （CI で完全一致検査。先頭トークンだけの照合は装飾つきトークンを見逃す）。
- **「表記を揃える」と「値を換算する」は別の作業で、正規化のときに分けて宣言しないと片方だけ残る**（2026-08-02・Issue #34）。
  2026-07-22 の events 日付 ISO 正規化は形式（`YYYY-MM-DD`）を揃えたが、**month 精度の値は旧暦の月番号が入ったまま**で、
  照合可能な 1389 フィールドのうち 1151（83%）が未換算のまま残っていた。同じ規約が適用済みだった `ages`・`reigns`・day 精度と
  食い違い、**同一レコード内で同じ事件が2つの日付表記で共存する**（`dongjin-andi` の弑逆が event では `0418-12-01`、
  `reigns.endDate`/`ages.deathDate` では `0419-01-28`）状態になっていた。年までずれる旧暦十一月・十二月の 105 件だけが目立ち、
  月だけずれる 1008 件は「別問題」に見えていたが、実体は1つの欠陥。
- **未換算の検出条件（ISO 月＝note の旧暦月）は、換算済みのフィールドを偽陽性で拾う**（同上）。
  ①旧暦九月の事件が太陽暦 9 月下旬に落ちれば月番号は一致する（**日に実値が入っている month 精度フィールドは日まで換算済みの疑いが高く、
  触ると改悪になる**。例 `wudai-houliang-modi` の `0914-09-23`＝乾化四年九月の実日付）②note に複数の旧暦月が出る期間イベントは、
  ISO 月がそのうちどれに対応するか機械では決まらない。**一括換算の対象は「日がプレースホルダ」「旧暦月が一意に決まる」で絞る。**
- **一括換算の前提は干支の実在チェックで自己検証できる**（同上）。「note の〇月〇〇（干支）がその旧暦年月に実在するか」を
  sxtwl で検査すると、照合できた 293 件中 282 件（96%）で「ISO 年＝紀年ラベル年・ISO 月＝旧暦月」という読みが裏付けられ、
  実在しない 20 件（朔差・史料誤記）を機械換算から外せた。**この検査は原典を読み直さずに前提の妥当性を測れるので、
  規模のある一括訂正では原典個別確認の前段に置くとよい**（残った少数だけを本紀で読む）。
- **期間を持つレコードの一括訂正は、条件をフィールド単位で書くと片端だけが動く**（同上）。`startDate`/`endDate` を独立に
  判定した結果、5 件で `startDate` > `endDate` の逆転が生まれ、31 件で1つのイベントの中に旧暦月と太陽暦月が同居した。
  **機械ゲートは端点の前後関係を見ていなかったので、訂正前後の差分を自分で突き合わせるまで表面化しなかった**
  （`validate_emperors.py` の event 検査は `date` のみ）。教訓は2つ: 条件と除外は**イベント単位**で書く。
  一括訂正の検証には「ゲートが緑」ではなく**訂正前後の差分に対する不変条件**（前後関係・片端だけ変わっていないか）を用意する。
- **暦の換算を検査するときは「値が正しいか」を順方向で判定する。「未換算か」を逆算しようとすると閏月で破綻する**（2026-08-02・Issue #34 フェーズ5）。
  多数月方式は旧暦月 → 太陽暦月の写像だが、**閏月のある年は2か月ずれる**（旧暦35年は閏三月があるため旧暦六月 → `0035-08`）。
  「ISO 月 8 なら旧暦八月の転記だろう」と読むと、正しく換算済みの値を未換算と誤判定する。実際この取り違えで
  一度は正しい値を巻き戻していた（`jin-huidi` の親征）。**判定は「その端点が指すべき旧暦月を原典で決める → 換算する → 現在値と比べる」の向きで統一し、
  逆写像（この太陽暦年月へ写る旧暦月は何か・全月を走査して求める）は補助に留める。**
  同じ理由で、**検出器も「ISO 月と note の旧暦月の一致」ではなく「note のどれかの旧暦月から換算した値と一致するか」で書く**
  （前者は訂正完了後も 127 件の偽陽性を出し続けた）。
- **史書の暦と推算ライブラリ（sxtwl）は朔・置閏がずれるので、月精度の値は「月ラベル」基準で換算する**（同上）。
  「note の干支がその旧暦月に実在しない」件を原典まで確認すると、月ラベル自体は原文どおりで（後漢書「三年春正月己未，大赦天下」・
  魏書「闰月癸丑，皇子生，大赦天下」＝魏書は閏四月・sxtwl は閏五月）、食い違いは暦法の差だった。
  **干支は日精度の情報なので、月精度フィールドの換算根拠にしない。**干支不在は「原典を確認せよ」という印であって、訂正の根拠ではない。
- **同じ意味のフィールドに表記が2種類あると、正規表現ひとつで母集団の大半が検査から抜け落ちる**（2026-08-02・Issue #34 フェーズ6）。
  month 精度の event 日付には `YYYY-MM-DD`（日はプレースホルダ）と `YYYY-MM`（日を持たない）があり、**多数派は後者（2464 対 1389）**だったのに、
  Issue のスイープもフェーズ1〜5 のスクリプトもすべて `^(-?\d{4})-(\d{2})-(\d{2})$` を要求していたため、
  **2464 フィールドが起票時から一度も検査されないまま「解消した」と結論しかけた**。気づいたのは、
  別件（端点の前後関係チェック）が `'1115-09'` のような値をそのまま印字していたのを見返したとき。
  **母集団を絞る正規表現を書いたら、「弾いた側」の件数と実例を必ず数える**（0 件であることを確認する、または内訳を出す）。
  検査対象の件数がフィールド総数と合っているかを一度突き合わせるだけで防げる。
- **「〇〇朝のデータ」の一括換算は、その王朝が旧暦を使っていた期間に限る**（同上）。
  `qing-xuantong` には満洲国期（1932-1945）のレコードが含まれ、「大同三年三月一日、即皇帝位」の三月一日は**太陽暦**。
  旧暦換算を当てると 1 か月ずれる。**王朝の終わりと暦法の切り替わりは一致しない**ので、
  近代にまたがる人物では対象年の暦法を確認してから換算する。

### 9-1. 日付の欠陥は5つの型に割れ、検出器はどれも1つの型しか見ていない（2026-08-03・Issue #55/#56/#57/#62 → #68 の教訓）

**元の Issue は 2026-08-03 に close したので、この節が working knowledge の正**です。残っている
件数は [RESIDUAL.md](RESIDUAL.md)（`記録` 列のコマンドで引き直せる形）にあり、ここには
**次に検出器を書く人が知っておくべき性質**だけを置きます。

**訂正が割れた5つの型**（#56 で親征イベントの終期42件を原典へ当て直し、24件が誤りだった内訳）:

| 型 | 例 |
|---|---|
| 旧暦の月番号を太陽暦の月欄へ直書き | 西夏襄宗 `1211-05`→**`1211-06`**（旧暦五月は西暦5月と1日も重ならない）・夏赫連定2件・後燕慕容盛・西夏景宗 |
| 起点と終期が別の旧暦月なのに同じ多数月へ潰れた | 明英宗の土木の変（七月＝1449-08／八月＝1449-09 が同じ `1449-08` に）・北魏太武帝・清聖祖 |
| 終期が帰還・終結の記事でなく「帝が自ら率いた最後の記事」 | 元世祖の阿里不哥親征 → 十二月甲午「师还」で **`1261-12-29`** |
| 年そのものがずれていた | 後燕慕容垂の翟釗親征 `0389`→**`0392`**（翟釗の継立が391年なので389年に攻めることは原文上ありえない） |
| 数日〜数十日の遠征を一点に潰していた | 遼聖宗（28日間）・明武宗の応州の役（本紀「战五日」と一致）・北斉武成帝・後燕慕容宝・北魏献文帝・晋恵帝 |

読むときに効いた性質を4つ:

- **「起点＝終期」は欠陥そのものではない。** 帝がその場で死んだ・捕虜になった・敵が去った型は
  本当に同じ月に収まる（読了42件中18件は現行が正しかった）。**形の一致は疑いであって欠陥ではない。**
- **absent 側（機械が何も見つけなかった側）は安全側ではなかった。** #56 の spanned バケットから
  種つき標本8件を原典で読んで**4件＝50%が取りこぼし**。#57 では日精度1,208件の absent から
  標本29件で反例2件（約7%）。**率は系統ごとに桁が違うので、系統ごとに測る。**
- **検出器の検出力は低い。** #55 の絞り込み（A＝干支不一致92件・B＝旧暦月日の直書き疑い14件・
  A∪B＝100件）は、既知の欠陥5件（#50）に対して**1件しか拾わなかった（1/5）**。残る4件は
  レコードの中に照合相手が無い（note が日付に触れない・干支が2つあって旧値がそのどちらかに当たる・
  干支が無い）。**「この検出器が出した N 件」は母集団ではなく、その検出器が見える範囲**。
- **原表記（`*Raw`）を足しても拾えない型がある。** #57 の「60日周期の別解」— 日干支は60日周期なので、
  **旧暦の月を同定せずに干支だけで西暦日を決めると、ちょうど60日ずれた別の日に当たる**
  （北宋仁宗 `1056-01-19`→**`1055-11-20`**・元英宗 `1321-12-18`→**`1320-12-23`**〔60日＋1年〕）。
  この2件はどちらも note に**正しい干支が書かれていた**。必要なのは原表記ではなく
  **「ISO 日付が属する旧暦月」と「記述にある元号年・月」を突き合わせる検出器**。

**この系統の欠陥は表現レベルで、集計統計を壊していなかった。** 2026-08-02 以降 `data/emperors.json` は
5,486行変わったが、8つの集計値の合計で動いたのは `crownPrinceDepositionCount` の 35→34 の**1つだけ**
（改元681・大赦1338・立后278・親征291・反乱鎮圧1494・被反乱1853・遷都57 はすべて ±0）。変更行の内訳は
`"count"` 22行に対して日付欄 3,967行・`note` 1,121行。**訂正の価値は「統計を直す」ことではなく
「同じ欠陥が二度と機械の目をすり抜けないようにする」ことだった**と、着手前に言えるようにしておく。

**副産物**: 「`datePrecision` が year なのに `endDate` に日まで入っていて、日精度で母集団を作る
検出器に最初から入らない」型（#68 のコメントで未計測とされていた）は、**#69 の移行後に実測して0件**。
いまの食い違い4,596件はすべて**値のほうが浅い**向きで、これは設計どおり
（`datePrecision`＝原典が何を言っているか／値の深さ＝配布物が主張する精度。規則 `R-DATE-CLAIM-SCOPE`）。

### 9-2. 歳首が動いた年では、`fromLunar(y,m,d)` の `m` が史書の月番号とずれる（2026-08-09・Issue #116 の1）

`sxtwl.fromLunar` は年号年と旧暦月をそのまま受け取る形なので、**その年の歳首が通常と違うと
月番号の意味が変わる**。唐の宝応元年（762年）がその実例で、`fromLunar(762,4,1)` は `0762-03-01`
（辛亥朔）を返し、この月は**まるごと太陽暦3月に収まる**（29日中29日）。旧暦4月が太陽暦3月に
落ちること自体がありえないので、ここで「ライブラリが壊れている」と読むと道を間違える。

**実測**（`fromLunar(762,m,1)` の朔日。`leap=True` を渡しても結果は同じで、762年に閏月は無い扱い）:

| m | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|
| 返る朔 | `0761-12-02` | `0761-12-31` | `0762-01-30` | `0762-03-01` | `0762-03-30` | `0762-06-27` | `0762-07-26` |
| 史書の月 | 上元二年十一月 | 十二月 | 宝応元年正月 | 二月 | 三月 | 六月 | 七月 |

**m=1〜5 は建子起算（夏正より2つ進む）・m=6 以降は夏正**で、`m=5`（`0762-03-30`）と `m=6`
（`0762-06-27`）の間が **89日空く**。史書の四月＝建巳月の朔 `0762-04-29`（庚戌）と五月朔
`0762-05-28`（己卯）は、**どの `m` を渡しても `fromLunar` からは引けない**。

背景にあるのは歳首の移動である。粛宗は上元二年（761年）九月に年号を廃して「元年」と称し、
**建子月（＝夏正の十一月）を歳首**とする紀月法へ移り、宝応元年四月の遺詔「建巳月为四月，
余月并依常数，仍依旧以正月一日为岁首」で元へ戻した。`fromLunar` の月番号はこの切り替わりを
またぐところで不連続になっている（`fromSolar` 側のラベルでは逆に `4月1日` が `0762-03-01` と
`0762-04-29` の2回現れる）。**実装が史実に忠実なのか、切り替わりの扱いを取りこぼしているのかは
確かめていない** — 確かめたのは上の表と、四月・五月の朔が引けないことまでである。

**判定に使うべきなのは月番号ではなく干支の連鎖**だった。旧唐書 巻十 粛宗紀が同じ年を
「建巳月庚戌朔」で始め、粛宗の没日を「丁卯」と書くので、庚戌朔＝`0762-04-29` から数えて
丁卯＝18日＝`0762-05-16` が出る。これは `tang-suzong.reigns[0].endDate` と一致し、玄宗紀の
「上元二年四月甲寅」の甲寅＝5日＝`0762-05-03` もそこから決まる。**朔日の干支が1つ与えられれば、
歳首がどこにあっても日は一意に決まる。**

- **踏むと何が起きるか**: この年の event に `source.conversion` として `fromLunar(762,m,1)` を
  書くと、`verify_calendar.py` の B-5 は**その conversion をそのまま再演して緑を返す** — 誤った
  多数月と保存値が揃っていれば、機械は2か月のずれを検出できない。**四月・五月については
  そもそも書けない**（引数が無い）。2026-08-09 時点で `emperors.json` に `fromLunar(762,...)` は
  1件も無い（`760`・`761`・`763` は在る）
- **同型が疑われる年**: 歳首が動いた期間は他にもある（秦・前漢の十月歳首は
  `R-DATE-CLAIM-SCOPE` の側で扱っているが、**唐のこの2年半は年号年ラベルごと動いた**ので
  性質が違う）。走査はしていない
- **手順**: 年号年ラベルが特殊な期間（「元年」「建子月」「建巳月」のような書き方が本紀に出る）に
  当たったら、`fromLunar` の結果を信じる前に**その月の朔日干支を本紀から引いて突き合わせる**

### 9-3. 帝紀の末尾に置かれた「要約」は年を取り違える — 志が第三の証人になる（2026-08-13・Issue #126 諡の段）

宋史・清史稿の諡の段（`name.posthumousNames`）を1冊ずつ走査して確定したときの教訓。

- **同じ書の中に、同じ事実の記述が2つの形で在る。** 帝紀の末尾は崩御に続けて
  「謚曰X，廟號Y。〈元号〉〈年〉，加謚Z」と**要約**を置き、日付つきの**条**は加諡を
  実行した後代の帝の紀に立つ。要約は読みやすいが、**年と形の組が壊れていることがある**
  — 宋太祖は大中祥符元年（玄功大孝の形）と天禧元年（聖功至明の形）の2回を要約が1つに畳み、
  **後の回の形に前の回の年を付けた**。宋哲宗は崇寧三年と政和三年の形を要約が入れ替えて書く。
  **どちらも要約だけを読むと矛盾に見えず、条を読むまで気づかない**
- **決め手は志。** 宋史 礼志の「加上祖宗謚號」節は同じ加諡を**日付つき**（年月日）で並べており、
  条と突き合わせると要約の側が畳んだ／入れ替えたことが決まる。**志は段を増やさないが
  年と字を裁定する** — 走査の前に「志には新しい段が在るか」だけを測って「無い」で閉じると、
  この裁定の役目を落とす
- **証人の数で決める。** 冒頭形と条が1字割れる型が宋で2人（真宗の應符／膺符・英宗の睿聖／睿神）。
  唐で決めた「割れたら証人の多い形を採る」がそのまま効き、どちらも条＋礼志の2証人の側になった
- **書が形を書かない回が在る。** 清史稿は加上の条を「加上〈廟号〉尊谥」で止めることが多く、
  **回が在ったことは条から分かるが形が分からない**（6回）。その裏返しとして**冒頭形のほうが
  崩御条より2字長い人物が3人**出る（聖祖の中和・高宗の欽明・宣宗の寛定）。
  **「冒頭形と段が食い違う」を1つの型として扱わない** — 宋の1字違い（異表記）と
  清の2字長い側（形を書かない加上の結果）は原因も対処も別で、**長さの向きが目印**になる

## 10. エージェント運用とドキュメントの設計（Claude 5 世代・2026-07-30 追記・Issue #15）

1〜9節は 2026-07-15〜27 の実測に基づく（使用モデルの記録は残していない）。**そこで得た運用方針（原典主義・自動生成禁止・引用の手打ち禁止・機械ゲート・id ピン留め・journal 経由マージ）はモデル世代に依らないので置き換わっていない。** 一方で「モデルの判断力を補うための細かい指示」は Claude 5 世代では不要になった（Anthropic は Claude Opus 5 / Fable 5 向けに Claude Code のシステムプロンプトの8割超を削って性能劣化がなかったと報告している）。本節はこの2つを分けて扱うための指針で、根拠にした資料は末尾に挙げる。

### 10-1. ドキュメントは「入口を軽く・詳細は都度」（progressive disclosure）

- **エージェント向けの入口（`CLAUDE.md`・`site/AGENTS.md`）は「リポジトリの目的」と「非自明な罠」に絞る。** ファイルを開けば分かること・一般的なコーディング作法は書かない。詳細は必要になった時点で開くリンク先（`docs/` 以下）に置く。2026-07-30 に `CLAUDE.md` から CONSTRAINTS.md の重複列挙と念押しの反復（「存在は知っている・前回読んだでは不十分」等）を落とし、代わりに WSL を落とすコーパス grep のような**罠**を1行で足した
  - **入口に残す基準**: 「リンク先を開く前に踏むと高くつく罠」（コーパス grep の OOM・並行セッションの上書き・外部 API の 429・ビルドが落ちる assert）だけを1行で置き、それ以外は正となるファイルへのリンクにする。ルール全文を入口へ写すのが重複、罠を入口に置くのは重複ではない
- **同じルールを複数ファイルに写さない。** 正となるファイルを決めてリンクする。重複は必ず片方だけ更新されて食い違う（進捗ドキュメントとデータ本体の `meta` で実際に起きた・6節）
- **矛盾する指示を並べない。** 「適宜コメントを残す」と「コメントを書くな」のような衝突は、モデルがどちらを取るかで挙動がぶれる元になる
- **説明よりリファレンスを渡す。** 文章で仕様を説明するより、確定済みの実データ・既存レコード・ツール出力を示すほうが正確に伝わる（このリポジトリでは `_corpus_cache/*.txt`・`scripts/quote_helper.py` の出力・`data/schema/` の実値例が既にその役割を担っている）
- **網羅的な例示でエージェントの探索を狭めない。** ただし判定基準の境界事例（3節）は「例示」ではなく判定内容そのものなので残す。区別の基準は [CONSTRAINTS.md](CONSTRAINTS.md) 冒頭「この文書の位置づけ」に書いた
- **`CLAUDE.md` をメモ帳にしない。** セッションをまたぐ状態は `docs/PROJECT_STATUS.md`・`task.md`・データ本体の `meta` が持つ（6節）。作業メモリはそのポインタに留める

### 10-2. 着手前に「未知」を減らす

成果物の質を決めるのは指示の細かさよりも**着手前に曖昧点をどれだけ潰したか**である（10-4 の Fable フィールドガイドの主題）。このリポジトリへの当てはめ（手順としては [RESEARCH_PROCESS.md](RESEARCH_PROCESS.md) の「0. 着手前に未知を洗い出す」）:

- 新しい王朝ブロック・新しい書に入る前に、**罠の洗い出し（blind spot pass）をエージェントに先にやらせる**〔推奨〕 — 3節・[CORPUS_NOTES.md](CORPUS_NOTES.md) の罠は、どれも「知らないことを知らなかった」ために踏んだもの
- 判定基準を新設・変更するときは、**一問一答のインタビュー形式**で「答えによって判定が変わる点」から潰す。基準の事前文書化＋ユーザー承認（3節）はこの具体化
- 調査中に出た**逸脱・境界事例はその場で記録**し、完了時に基準文書へ反映する（3節「境界事例の都度ルール化」と同じ。後からは思い出せない）

### 10-3. ハーネス（Workflow）の設計 — パターンの使い分け

Workflow は「複数エージェントをどう配置するか」を都度書けるので、タスクの形に合わせてパターンを選ぶ。〔実績〕はこのリポジトリで実際に使った形、〔推奨〕は今後この形にするとよいという提案（まだ実施していない）：

| パターン | このリポジトリでの用途 |
|---|---|
| **fan-out-and-synthesize**（並列分割→最後に統合） | 〔実績〕人物ごと1エージェントの本紀通読（3節）。バリア（全件を待ち合わせる同期点）は「全部を並べて初めて判断できる工程」＝重複排除・0件時の早期終了だけに置く。単に flatten/filter したいだけならバリアは不要 |
| **adversarial verification**（別エージェントに反証させる） | 〔実績〕引用・note の検証（8節）。**エージェントの「全件シロ」報告はアンカリングを疑い、陽性・陰性の両側を別コンテキストで抜き打ち再検証する**。自分の出力を自分で検証させると甘くなる（self-preferential bias） |
| **loop-until-done**（見つからなくなるまで回す） | 〔推奨〕悉皆性の監査。固定回数・チェックリスト消化型は末尾を取りこぼす（4節「完了宣言の前に必ず悉皆実測する」）。唐哀帝の収録漏れを見つけたのはエージェントのループではなく在位年カバレッジの機械集計（1節）で、監査の起動条件として「新しい欠落が出なくなるまで角度を変えて回す」形にできる |
| **classify-and-act**（分類してから振り分け） | 〔推奨〕訂正 Issue の切り分け（データ誤り／表示不具合／収録基準の議論）。誤った窓口に入れると調査コストが跳ねる |
| **generate-and-filter / tournament**（候補を出して選抜） | 〔推奨〕サイト掲載文言・説明文の案出し。**データ判定には使わない**（判定は個別調査・3節） |

- **部分完了で止まる（agentic laziness）・自分の結果を甘く採点する（self-preferential bias）・当初の目的から逸れる（goal drift）は、単一コンテキストで長く回すほど出る。** 検証はプロンプトの念押しではなく**別エージェント・別コンテキストへ分ける構造**で防ぐ
- **Workflow を使わない判断も明示的にする。** トークン消費が大きいので、1〜2人分の訂正や1ファイルの文言修正は単発の Agent か手作業のほうが速く安い（5節の実測でも、少人数の修正は対象を絞った小さい Workflow が安全だった）。必要なら「10k トークンで」のように上限をプロンプトで与える
- 5節の実測（`resumeFromRunId` のフルリラン事故・15人超のまとめタスクは人物単位に分割・args はエージェント自身に jq で取らせる・独立なツール呼び出しは1レスポンスに束ねる）と、4節の id ピン留め・journal 経由マージは**このリポジトリでの計測結果なので、上のパターン語彙で置き換えない**

## 11. 生成の順序が正確さを決める（2026-08-02・紹介文 Issue #16 の教訓）

調査の正確さと、その調査結果を**文章にするときの正確さ**は別ものです。データ側は全12項目×365人を
原典で確定させたのに、それを素材にして書いた紹介文には主語・世代・月の取り違えが出ました。

### 11-1. 素材を先に読むと、素材の筋書きに合う原文を探すことになる

当初の手順は「素材（`emperors.json` の note）を読む → 原文で確かめる → 書く」でした。これだと原文が
**確認**の位置に落ち、note の誤りがそのまま本文へ流れます。実際、敵対的検証で出た誤りの多くは note 由来でした
（桓玄「詔を書いたのは臨川王宝」＝原文は否定が落ちて逆の意味・苻生「皇太子として桓温を迎え撃った」＝
354年の太子は兄の苻萇）。**note と原文の食い違いは 2026-08-02 時点で59件**（Issue #32・#33 は訂正済み、#36 は未訂正）。

順序を「**原文を読む → 引用台帳（`claims`）を作る → note を照合として読む → 台帳の範囲だけで書く**」へ逆転しました。
台帳に載らない事実は書けません。**本文を先に書いて後から根拠を集めない。**

### 11-2. 「食い違いがなかった」を明示的に言わせる

エージェントの最終メッセージは短くさせているので、note と原文が食い違っても**黙って原文を採って終わる**ことがあります。
これでは親セッションがデータ側の誤りに気づけません。**「食い違い: なし」と書かせる**——無言を「照合した」と読まない。

### 11-3. 機械ゲートは「エラー0」より「報告を読ませる」ほうが効く

字数・ルビ・重複は機械で落とせますが、事実の誤りは落とせません。代わりに**判断材料を書き手の目の前に出す**:

- 引用台帳の各句が本紀キャッシュに実在するか（最長共通部分列の被覆率。記憶で書いた断片は 0.5 を割る）
- 本文に出てくる年・人数・年齢のうち**台帳に無いもの**
- `accessionRoute.axes.relationToPredecessor` と本文の続柄語の食い違い（**判定はしない**。
  本文の続柄語が前任者を指しているとは限らない）

続柄の一般的な機械照合（「兄の李蕩の子」のような第三者どうしの関係）は**やらないと決めました**。
`data/kinship.json` の収録は皇帝と一親等が中心で、ブロックによっては数人しかありません。
**空の照合が緑で通ると「確かめた」と読めてしまう**のが一番危険です。書き方の規則に落として、
「**原文が続柄を直接述べていない関係は書かない**」としました。

### 11-4. Web は根拠ではなく差分検出器として使える

1節の「AIの要約を判定根拠にしない」は**データ判定の規則**です。文章化の段では、通説と食い違う箇所を
**原典を読み直す引き金**として使えます（2026-08-02 ユーザー決定）。ただし
**Web の文章・言い回しを本文へ取り込まない**（CC BY-SA 混入のスクリーニングを過去に実施している）。
「通説と違うが原典に従った」ケースは根拠欄に1句残さないと、次の照合で同じ差分が挙がり続けます。

### 11-5. 規則の適用範囲が書かれていないときは、勝手に決めずユーザーに聞く

上記の Web の扱いは、規則側に適用範囲が書かれていなかったために「紹介文にも掛かる」と判断し、
Web 照合をしないまま76人ぶんを公開した結果として決まりました。ユーザーの想定はデータ判定のみでした。
**規則を自分の解釈で広げる／狭める前に聞く。** 規則を書くときは適用範囲も書く。

### 11-6. 弱いレビューアの「指摘が少ない」を品質だと読んでいた（2026-08-12・紹介文228本の外部レビューの反省会）

228本を書き終えたあとで opus-5＋Web検索・1本1体の外部レビューを回したところ、
**1本あたり28〜30件**の指摘が出た（2026-08-12 のセッション時点で47本1,302件。**取得は進行中**
なので総数は動く。引き直しは `ls review/result/*.md | wc -l` と
`cat review/result/*.md | grep -c '^| \['`）。**まず数の読み方から** — 下の表の上2行は
**同じ24本で閉じた対照**なので動かない:

| 測り方 | 母集団 | 指摘 | 1本あたり |
|---|---:|---:|---:|
| 2026-08-09・gemini-3.6-flash | 同一24本 | 200 | 8.3 |
| 2026-08-12・opus-5＋Web検索 | 同一24本 | 716 | 29.8 |
| 2026-08-09 に**採用**した箇所 | 228本 | 458 | 2.0 |

**991 と 458 は同じ測り方の数ではない。** 同じ本文に対して 3.6倍の差が出ており、差の大半は
文章の劣化ではなく**測る道具**（レビューアの能力と、Web検索という別の情報源）。同じ日に
組んだ2レンズ版はさらに倍（3本で62/60/81件）出したが**観点1では単体に負けた** — 効いたのは
体の数でも思考量でもなく Web検索だった。したがってこの件の本当の答えは
「品質が崩れた」ではなく、**「文章はおそらく最初からこうで、工程が持っていた品質の信号が
弱すぎて見えていなかった」**。

#### 内訳 — 崩れたのは事実の層ではなく「読者に通じるか」の層

観点別（47本1,302件の時点。**割合で読む** — 引き直しは
`awk -F'|' '/^\| \[/ {gsub(/ /,"",$3); print $3}' review/result/*.md | sort | uniq -c | sort -rn`）:
1通説割れ 318（24%）／5一読で入るか 293（23%）／4語がその場で通じるか 222（17%）／
9ルビ 177（14%）／2条の融合 123（9%）／8訓読調 63／3内心の断定 37／7水増し 36／6主観評価 23。

**4と5だけで4割**。ここが崩れた層で、しかも**原文を持たなくても判定できる＝空振りしにくい**
観点でもある。9（ルビ）を足すと54%になるが、9には既知の空振りの型がある —
「一般語なのに振っている」型が177件中26件（15%）あり、`data/profile-ruby-lexicon.json` に載る語は
**必ず振る語**なので外すと他の本と割れる（review-21 の「武帝」「始皇帝」3件はこれで不採用）。
**9は辞書と突き合わせるまで件数が確定しない。**

観点1・2の**標本12件**（秦始皇帝・二世・漢高祖の3本ぶん。**いずれも最初期のバッチで、
王朝の偏りがある**）を原文へ当て直した結果:

- **設計どおり（原文採用・非欠陥）** — 少子胡亥→「末子」・中子・呉王「兄」・周章・
  「杀陈胜城父」・「六公子戮死於杜」・「立二世之兄子公子婴」・辒凉车・徐巿。規範
  「割れたらデータ（＝原典）を採る」に従った結果で、依頼文も「通説ではこう」の形で
  挙げるよう指示している
- **空振り** — 荊軻（原文「秦王覺之，體解軻以徇」）・章邯の連戦（原文「杀陈胜城父，破项梁
  定陶，灭魏咎临济」）。原文がそう書いている。README に既にある観点3の空振り率
  （review-08 で10件中9件）と同じ形で、**レビューアが原文を持たない構造から出る**
- **本文側の実欠陥** — 「三十年、無事」を**四文字**と書いた箇所（原文「三十年，无事」＝5字）・
  酈商が説いた相手（審食其）が落ちて呂后へ直接説いたように読める箇所・沛の父老が
  「陳勝の挙兵に応じた」主体になっている箇所

つまり**この標本の範囲では事実の層は持ちこたえ、崩れたのは読者に通じるかの層**だった。
**3本12件の標本なので、事実／読みやすさの割れ方そのものが未測定**（`RESIDUAL.md` の行）。
そして「読者に通じるか」は軽い層ではない — サイトの読者が受け取るのはその層しかない。

#### なぜ止められなかったか — ゲートは全部「在るか・形が合っているか」しか見ない

字数・ルビ辞書の網羅・12-gram・`claims` の実在照合・`ARCHAIC` 語彙。**どれも判断を要しない
検査**で、緑であることは「原文を開いて書いた形跡がある」以上を意味しない。一方で指摘の
上位クラスは全部**判断のクラス**だった。しかも**規範自身がそう書いていた**:

- SKILL.md「ルビは読みの手当てでしかない。読めても意味が分からない語は地の文で意味が通るように
  書く。**ここは機械では見られない**」→ 観点4が181件
- README「本どうしの型の反復は**機械では見られない**」（12-gram は12字連続でしか当たらない）
- README「訓読調は**文言だけでは止まらなかった**」（18本54箇所）→ 今回も観点8が54件。
  `ARCHAIC` は固定語彙なので、語を替えれば抜ける

**「機械では見られない」と書いた時点で、そこは人か外の目が要ると決まっていた。**
それなのに強いレビューアを入れたのは228本目だった。08-09 に入れた外の目は
gemini-3.6-flash で、その 1本8件・採用2件という低い数字を「この程度で済んでいる」と読んだ。
**弱い測定器の低い値を品質の根拠にしない** — 8-2「検証器の緩さは欠陥そのものより長く生き残る」
の、散文版。

#### これは新しい教訓ではなかった

同じことは既に書いてあった（メモリ `visual-quality-needs-outside-eye-first.md`:
**見た目が目的の工程は着手前に外部評価を取る／ゲート通過数を品質の根拠にしない**）。
サイト設計の教訓として綴じてあったので、散文の工程では発火しなかった。
**教訓は綴じた場所が適用範囲を決めてしまう**（`R-SCOPE-ASK` と同じ形）。

#### 費用の非対称 — 「トークンをかけたのに」ではない

失敗はコストの掛け方ではなく信号の取り方の側にある。SKILL.md の最適化（原文1巡・advisor 禁止・
規範文書を読ませない・`basis` はポインタ）はどれもこの失敗と**直交**する。10本目で強い
レビューアを1回回していれば、出た指摘は**クラスとして執筆プロンプトへ1回で返せた**。
228本目で回すと、同じ内容を**1本ずつ当て直す**作業になる（28件×228本）。
**弱いレビューアの安さは、指摘を1件ずつ当て直す費用になって返ってくる。**

#### 指摘の生データがリポジトリの外にある

`review/` は `.gitignore` 対象で、2026-08-12 に1人1ファイルへ切り替えたとき**既存の書き出しを
全部消して取り直した**。その結果、08-09 の指摘200件の生データはもう無く、残っているのは
コミットメッセージの「採用したN箇所」だけで、**不採用にした指摘が何だったかは追えない**。
採用率も、同じ指摘が次のレビューで再び出たかも測れない。**外の目の出力は配布物ではないが
記録物**なので、`data/internal/` 側へ残す（`R-CLAIM-GATED` が内部側へ置けと言っているのと
同じ理由 — ゲートは書けないが、witness としては要る）。

#### 測っていないこと

レビュー済みは id 001〜047 の範囲の35本だけで、**唐・北魏・隋の密度は未測定**。
228本が一様にこうだとは言えない。残りは残量表の行。
