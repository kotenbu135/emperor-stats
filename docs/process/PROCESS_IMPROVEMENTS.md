# 手順の改善提案（採否の記録つき）

調査の最中は、手順のどこが効いていないかが一番よく見えます。ところが**その場で書かないと
思い出せない**ので、気づいた時点でユーザーへ提案し、採否をここへ1行で残します
（規則 `R-PROCESS-FEEDBACK`・[RULES.yml](RULES.yml)）。

- **採用**したら、正となるドキュメント（RESEARCH_PROCESS・CORPUS_NOTES・RULES.yml・
  エージェント定義・スキル）を同時に直す。ここは記録であって規則の置き場ではない
- **却下**も残す。理由を書いておかないと同じ提案が繰り返し挙がる
- **提案者はエージェントでもよい。** 調査エージェントの出力には `processSuggestion` という
  任意の欄があり、検証エージェントは報告本文に「手順の提案:」と書く。どちらも
  **`.claude/hooks/suggestion_capture.py`（Stop フック）が turn の終わりに末尾の
  「自動採取」節へ写す**ので、親セッションが書き落としても消えない
- **親セッション自身の提案は自動では拾えない**（地の文に機械が読める印が無い）。
  `python3 scripts/add_suggestion.py --auto --title … --scene … --body …` を自分で呼ぶ。
  採否が決まったものを本文へ足すときは `--auto` を外す（`--verdict` で採否を書く）
- **採用した提案の実施管理は GitHub Issue #41**（実施順つき）。ここは採否の記録、
  向こうは残作業の一覧。**両方に同じ本文を置かない**

## 書き方

```markdown
### YYYY-MM-DD 〈一行の見出し〉
- **気づいた場面**: どの作業のどこで
- **提案**: 何をどう変えるか
- **採否**: 採用（反映先: ファイル名）／却下（理由）／保留
```

### 2026-08-02 検証の体数を欠陥密度に合わせる

- **気づいた場面**: RESEARCH_QA_PLAN 2節の実測で、欠陥密度は一様でなく3段の階段だった
  （前漢・後漢・三国 43人＝0件／晋 15人＝6件・0.40／小政権＋五胡十六国 18人＝28件・**1.56**）。
  なのに検証はどのブロックでも同じ段数で回している
- **提案**: 正史の本紀が独立して立つ王朝は検証1体、**載記・類書・地方志に依存する政権は3体**
  （事実・続柄・日付の別観点）。総コストをほぼ変えずに密度の高い側へ寄せる。
  効いたかは「検証段の指摘のうち実欠陥だった率」をブロック別に記録して測る
- **採否**: 採用（実施順 5／管理は Issue #41・2026-08-02 ユーザー決定）
- **実装**（2026-08-02）: 規則 `R-VERIFY-TIER`（L2+L3）。記録は `data/verification.json`、
  ゲートは `scripts/check_verification.py`（`--for <id>` で体数と観点、`--scope` で内訳、
  `--rate` で指摘率）。`.claude/workflows/name-block.js` が調査段の返した tier で
  検証エージェントの数を1体／3体に変え、`.claude/agents/adversarial-verifier.md` と
  `VERIFIER.md` が観点（`facts`／`kinship`／`dates`）の指定に従う
- **形式で割ると蜀漢・呉が落ちる** — 「本紀があるか」で機械的に割ると三国志の蜀書・呉書は
  伝の体裁なので `dependent`（3体）になるが、実測の欠陥密度は0件だった。
  割るべきは形式ではなく「**一代を通す独立記述があるか**」で、先主傳・吳主傳はそれに当たる
- **1体へ減らす側にだけ根拠を要求する** — 3体に増やす誤りはトークンを損するだけだが、
  1体に減らす誤りはその政権の誤りを通す。だから既定を `dependent` に置き、
  `own-annals` にだけ書名・所在・体裁を必須にした。記録漏れは厚い側へ倒れる（89政権中58政権が既定）
- **モデルは3段の階段のうち2段しか説明しない** — 晋（0.40件/人）は本紀を持つのに
  前漢・後漢・三国（0件）と差がある。史料形態が説明するのは「原典から取れるか」の側だけで、
  同一レコード内の食い違いと note の陳腐化は Issue #40 のゲートの担当。
  **説明できていないことを承知で体数を振っている**ので、`raised`／`confirmed` を記録して
  後から反証できる形にした（未検証の仮説をゲートに固定して反証不能にしない）
- **総コスト中立ではなかった** — Issue の「総コストをほぼ変えずに」は、薄い側から引ける余地が
  あることを前提にしていたが、薄い側はすでに1〜2段まで削れていた。実測で原文突き合わせは
  365体 → **619体**（own-annals 238人×1＋dependent 127人×3）。紹介文は1人2段の 730体 →
  984体（+35%）。中立にするなら `own-annals` の Web 差分を落として 746体（+2%）にできるが、
  Web 差分は2026-08-02のユーザー決定なので**勝手には外していない**
- **3体の指摘は畳んでから数える** — 体ごとに数えると同じ欠陥を3回数えることになり、
  「体数を増やしたら指摘が増えた」が自動的に成立してしまう。`(field, problem)` で一意化した
  件数を `raised` にし、畳む前の件数は別に出す
- **体数の効果は同じ tier の中でしか読めない** — 体数と欠陥密度は交絡している。
  tier をまたいで指摘率を比べても、差が体数のせいか政権のせいか割れない

### 2026-08-02 政権単位で決まることを人物単位で365回やらない

- **気づいた場面**: #37（名前の悉皆補充）の構造を実測したところ、**89政権・365人**で、
  廟号は「政権の全員が空」が **64政権・173人**、1政権あたりの人数は中央値2・1人だけの政権が34件
- **提案**: 「この政権は廟号を立てるか」「元号呼称が主流か」は**政権の慣行**なので、
  本紀冒頭の書式で**政権単位に先に確定**し、人物単位の調査は残りに絞る。
  #24（dynastyOrder・51政権190人）はもともと政権単位の作業なので同じ形が効く。
  **空欄が取りこぼしの可能性もあるので、慣行の確定も原典で行う**（自動補完はしない）
- **採否**: 採用（実施順 1／管理は Issue #41・2026-08-02 ユーザー決定）
- **実装**（2026-08-02）: 規則 `R-REGIME-FIRST`（L0+L3）。記録は `data/regime-conventions.json`、
  ゲートは `scripts/check_regime_conventions.py`（`--scope` で母集団 N → 要調査 M、
  `--for <id>` は未確定の政権で 1 を返す）。`.claude/workflows/name-block.js` の
  `regimeConvention` を必須欄にして、未確定の政権では人物単位の調査を立てられなくした
- **設計で効いた点**: **記録するのは「値」ではなく「書式・所在」**にした。
  「唐は全員に廟号がある」は人物単位の主張で24人読まないと言えないが、
  「舊唐書は本紀冒頭に廟号＋諡号＋諱を並べる」はサンプル数件で立ち、誰の値も先決めしない。
  そのうえで人物単位の問いが**判定から転記に変わり、3項目が1回の読みで同時に取れる**
- **測る**: パイロットで **8政権60人**（唐24・明16・前漢14・秦2・新1・玄漢1・成家1・仲家1）を確定。
  廟号でみた内訳は転記36人・別所在4人・**絞り込めず人物単位のまま18人**。
  絞り込めなかった前漢14人が重要で、機械の書式当たり（冒頭3行の「讳/諱」）は0件だったが、
  **これは廟号が無いのではなく漢書が冒頭に並べないだけ**だった。
  政権単位に「値」を書いていたら14人ぶん誤って確定していた
- **例外は政権の判定を被らない**: 唐24人のうち4人は帝紀に独立記述が無く所在が違う。
  記録が `form-found`（＝転記）なのを人物にもそのまま被せると、**所在の違う4人が
  「書き写すだけ」に見える**。例外は自分の `personScope` を持つことをゲートで要求している
- **見落としていた非対称**: 「書式がある」を誤ってもトークンを損するだけだが、
  「無い」を誤ると**その政権の空欄を全件まとめて「正しい」と結論する**。
  打ち切り側の判定にだけ、対象政権それぞれの原典の裏をゲートで要求している

### 2026-08-02 原典を読む前に機械で前提を検証して母集団を絞る

- **気づいた場面**: Issue #34 で「note の干支がその旧暦年月に実在するか」を sxtwl で検査したら、
  照合できた293件中**282件（96%）**で前提が裏付けられ、**残り20件だけ**を本紀で読めばよくなった。
  #38 も `quote_diff.py` で234件を仕分け済み（一致32・1字違い42・2字20・3字以上29・近い箇所なし111）
- **提案**: これを**新規調査の前段の定型**にする（`/research-block` の手順へ）。
  原典読解のトークンは母集団に比例するので、絞り込みが最も大きく効く
- **採否**: 採用（実施順 3／管理は Issue #41・2026-08-02 ユーザー決定）
- **実装（2026-08-02）**: 規則 `R-SCREEN-FIRST`。絞り込みは `scripts/screens/<名前>.py` に
  コミットし、結果を `data/screenings.json` へ記録する。ゲートは `scripts/check_screenings.py`
  （CI・Stop フック）。L0＝`.claude/workflows/name-block.js` が `screenBucket` を必須欄にした
- **記録ではなくスクリプトを走らせて突き合わせる**: 記録した数字だけが残ると、データが動いた
  あとも「絞ったつもり」で緑になる。ゲートは毎回 screen を実行して件数を比べ、ずれたら落とす
  （調査が進めば母集団は減るので、件数だけを機械が直す `--update` を用意した。
  kind・means・監査には触らせない）
- **`absent` は不在の証拠ではない**: バケットを3種に割った — `read`（要読解）／`corroborated`
  （独立した計算か原典の明文が前提を**積極的に裏付けた**。#34 の sxtwl 検査がこれで標本は要らない）／
  `absent`（機械が何も見つけなかっただけ）。**厚い根拠を要求するのは absent だけでよい**
  （実施順1で見つけた非対称性と同じ形）
- **測ったら実際に漏れていた**: Issue #37 の名前データで標本監査を掛けたところ、諡号の absent 側は
  **6件中3件が取りこぼし**（北宋神宗・金哀宗・明英宗）。廟号で呼ばれる皇帝は commonName が
  「神宗」になるので、諡号が本紀冒頭に並んでいても検査に当たらない。**#37 の113件・58件は
  作業量の下限であって総量ではない**ことが数字で出た
- **標本は機械が引く**: 人が選んだ標本では 3/k の上限を言えない。スクリプトが種から引き、
  ゲートが同じ種で引き直して突き合わせる。抽出は `random.sample` ではなく**ハッシュ順の上位 k**に
  した — 母集団が動いても他のセルの増減が既存の標本の当落を変えないので、調査が進んでも
  監査をやり直さずに済む
- **「監査した」だけでは何も言っていない**: 出力に取りこぼし率の95%区間（Clopper–Pearson）を
  必ず出す。反例0件でも k=6 なら上限46%で、10%以下と言うには30件要る。
  Issue #40 のゲートで得た「0エラーは綺麗と空回りを区別しない」と同じ話

### 2026-08-02 完了判定を毎回データ本体から実測する

- **採否**: 採用（実施順 4／管理は Issue #41・2026-08-02 ユーザー決定）
- **実装**（2026-08-02・規則 `R-COVERAGE-MEASURED`）: `scripts/coverage.py`。
  L3＝`--check`（CI ＋ Stop フック。`emperors.json`・`kinship.json`・`emperor-profiles.json`
  のいずれかを触れば流れる）／進捗表記は `docs/PROJECT_STATUS.md` の
  `<!-- coverage:begin -->` … `:end` を `--write` が生成する
- **「在るか」で数えると全項目が緑になる**: 12項目はトップレベルのフィールドを全員が持っており、
  存在で数えると 365/365 が並ぶ。その状態でも Issue #37 の562セル・紹介文の残り289本は1件も

- **確定の根拠が散文にしかない項目は unknown へ落とす**: `ages` には「調査したが原典に記載が無い」
  の構造的な印が無く、note の文にしかない。**note は作業ログなのでフィールドとの突合は向きが

  結果 `ages` 4項目の557セルが unknown へ出たが、**それが所見**であって、スクリプトが
  どちらかへ寄せてよいものではない
- **`confidence` を確定の印に流用しない**: `ages.confidence` は一見使えるが、実測すると
  **high の98人が `accessionAge` を持たない**。レコード単位の判定であってサブ値の印ではない。
  「使えそうな既存フィールド」は流用する前に反例を数える
- **導入時の実測**: 完了と称している16項目5858セルのうち **637セル（10.9%）が構造だけでは
  確定と読めなかった**（`ages` 4項目557・在位日80）。「誤っている」ではなく「**完了の主張が
  機械では確かめられない**」であり、この区別を出力に書いておかないと次に読む人が数字を誤読する
- **同じ母集団を測る道具は2つ持つと検算になる**: 名前2項目について `coverage.py` は

  同じ562に落ちた**。片方が片方を import すると、この突き合わせは何も検査しない
- **政権別は昇順で見る**: 大きな政権が平均を持ち上げる。実測でも確定率の下位は1人だけの政権が

  同率が並ぶ帯**なので、手当ての量は判別不能セル数の多い順で見る（出力は両方出す）
