# emperorstats.com SEO 実行計画

作成日 2026-07-27。根拠は [FULL-AUDIT-REPORT.md](FULL-AUDIT-REPORT.md) と `findings/` 各ファイル。

## この計画の前提

- **Critical（インデックスを阻害する・ペナルティを招く）判定の指摘は1件もない。** 以下はすべて「良好な土台の上での改善」であり、緊急対応を要するものはない。
- **Search Console を前提とする指標は使わない。** GSC 連携はユーザー決定で対応しない方針（2026-07-24）のため、各項目の先行指標は `curl`・`grep`・ブラウザ・AI への問い合わせなど GSC 無しで観測できるものに限定した。`findings/` 配下の個別ファイルには GSC 前提の記述が残っているが、**この計画側の指標が正**。
- **公開から9日**（2026-07-18）。順位・インデックス・被リンクに関する指標は、そもそも成果が出るのに時間がかかる段階にある。この時期に順位を見ても意味がないため、下記の指標はすべて「実装が正しく入ったか」を測るものにしてある。
- 本監査は**報告のみ**。コード・データは一切変更していない。

## Phase 1 — 既存パターンの横展開（今週）

このフェーズの4項目は**すべて「他ページではすでに正しく実装されている型を、抜けている場所に当てる」作業**であり、新しい設計判断を必要としない。1つのブランチでまとめて完結できる。

### 1-1. `/death-accession` と `/dynasties` に静的な数値リストを追加する ★最優先

- **根拠**: `/death-accession` の本文は314字で、死因8分類のうち実数がテキストにあるのは「病死161名44%」の1件のみ。残り7分類は円グラフ SVG の中にしか存在しない。`/dynasties` は483字で王朝別平均在位年数の一覧がテキストに無い。一方**トップページ `/` には8分類すべてがテキストで載っている** — 専用ページの方が情報量で負けている。
- **やること**: 既存の共通部品 `site/src/components/tables/top-ranked-table.tsx`（`reign`・`ages`・`military`・`court-events` の4ページで使用中）を `death-accession`・`dynasties` にも適用する。データは `data/emperors.json` から機械集計できる**表示形式の変更のみ**で、原典の再調査は不要。
- **これが解除するもの**: 1-2（読み取れること文の追加）、Phase 3 の SXO 施策（「皇帝 暗殺 割合」等のキーワード空白地帯の獲得）、GEO の Citability 改善。**この項目を先にやらないと下流の施策は効かない。**
- **失敗判定**: 追加後、AI（ChatGPT/Perplexity）に「中国皇帝 死因 内訳」と聞いても本サイトの数値が引用されないなら、原因は本文情報量ではなく被リンク・認知度（Phase 3）。
- **先行指標**: `curl -s https://emperorstats.com/death-accession | (タグ除去して文字数)` が 314字 → 800字以上になること。

### 1-2. 「読み取れること」文をセクション単位で埋める

- **根拠**: 統計6ページに存在する16セクションのうち、直接回答文があるのは7セクション（44%）のみ。`court-events` は5ランキング中1つ、`military` は3ランキング中1つ、`reign` の復位者一覧には無い。
- **やること**: 既存パターン `「〜が最も多いのは◯◯で、△件です。」` を残り9セクションに1文ずつ追加する。
- **失敗判定**: 追加後も AI が本サイトを情報源として挙げないなら、文の有無より外部シグナルが支配的。
- **先行指標**: `grep -c "読み取れること" out/*.html` の合計が 7 → 16 になること。追加前後で ChatGPT/Perplexity に「改元・大赦・立后・皇太子廃立・遷都・反乱鎮圧・被反乱の最多は誰か」の7問を投げ、本サイトが挙がる回数を手動比較する。

### 1-3. `/emperors` の meta description を他ページ水準に揃える

- **根拠**: 22字（他の統計8ページは60〜76字）。サイト最大のハブページでここだけ手薄。
- **失敗判定**: 差し替え後、`site:emperorstats.com/emperors` のスニペットが新しい文にならず Google が本文から別の文を拾うなら、description ではなく本文側の問題。
- **先行指標**: ブラウザで `site:emperorstats.com/emperors` を実行しスニペット表示文を確認（1〜2週間で反映）。

### 1-4. GitHub リポジトリの `homepage` / `description` / `topics` を設定する

- **根拠**: いずれも未設定。設定するだけで、リポジトリページ上部・GitHub 検索・トピック集約ページ（GitHub 公式管理の高権威ページ）からの恒常的な導線が増える。**コード変更ゼロ・数分で完了**。
- **先行指標**: リポジトリページ上部に `emperorstats.com` のリンクが表示されること。

## Phase 2 — 構造の是正（2〜3週間）

### 2-1. サイドバーの空 `<h3>` を解消する

- **根拠**: 全378ページに、テキストが空の `<h3>` が7個ずつ、h1 より前に出力されている。shadcn/ui の `AccordionTrigger` が既定で `AccordionPrimitive.Header`（= `h3`）を出力し、見出しテキストは h3 の外側の `<a>` にあるため。
- **やること**: `Header` に `asChild` を渡して `div` として描画するか、ナビ用アコーディオンだけ `Header` を使わない派生にする。ナビゲーションは見出しではないので `h3` である必然性がない。
- **失敗判定**: キーボード操作（アコーディオンの開閉）が壊れるなら、`Header` を残して `sr-only` テキストを入れる方式に切り替える。
- **先行指標**: ビルド後 `grep -o '<h3[^>]*data-orientation' out/index.html | wc -l` が 0。

### 2-2. 皇帝個別365ページの h1→h3 レベル飛びを直す

- **根拠**: 365ページ全件で h2 が存在せず h1 から h3 へ飛んでいる（「即位の経緯」「死因の経緯」「関連動画」）。サイトの96%を占める面なので影響範囲が大きい。
- **やること**: これらを `h2` にする。視覚上の階層が崩れるなら CSS で見た目だけ従来どおりにする。
- **先行指標**: ビルド後、見出しレベル飛びの検出が0件。

### 2-3. 皇帝個別ページ → 統計ページの文脈内リンクを追加する

- **根拠**: 365ページすべてで、本文から統計6ページ（`/reign` 等）へのリンクが**0件**。個別ページには「365人中◯位」という順位が大量に表示されているのに、対応するランキングページへ導いていない。365ページ分のリンク資産が統計ページに届いていない。
- **やること**: 順位表示のそれぞれを、対応するランキングページへのリンクにする（例:「在位年数 365人中12位」→ `/reign` へ）。同様に統計ページ間の相互リンク（現状0件）も検討する。
- **これが解除するもの**: 統計6ページの内部リンク評価。Phase 1-1/1-2 でページ内容を厚くした効果を、リンク構造の側から支える。
- **失敗判定**: リンク追加後も統計ページのクロール頻度が変わらないなら、内部リンクではなく外部シグナルが律速。
- **先行指標**: ビルド後、皇帝ページ1件あたりの統計ページへの発リンク数が 0 → 数本になること（`grep` で確認可能）。

### 2-4. Cloudflare 側でセキュリティヘッダと URL 正規化を入れる

- **根拠**: HSTS・X-Content-Type-Options・Referrer-Policy・CSP・Permissions-Policy が全欠。`/reign/` 等の trailing slash 付き URL が全ページ404。`/index.html` が301されず200で二重配信。`www.emperorstats.com` は DNS 未解決。
- **やること**: GitHub Pages はカスタムヘッダ非対応だが、**本サイトはすでに Cloudflare を通っている**（`server: cloudflare` を実測確認）。Transform Rules でヘッダ付与、Redirect Rules で `/xxx/` → `/xxx` と `/index.html` → `/` の301を設定できる。`www` は CNAME を追加するかどうかの判断。
- **注意**: これはサイトのコードではなく**インフラ設定の変更**。CSP はサイトを壊しやすいので、まず `Report-Only` から始めること。
- **失敗判定**: CSP 適用後にチャート・フォント・YouTube サムネイルが読み込めなくなるなら、ポリシーが厳しすぎる。
- **先行指標**: `curl -sI https://emperorstats.com/` に `strict-transport-security` が現れること。`curl -s -o /dev/null -w "%{http_code}" https://emperorstats.com/reign/` が 404 → 301 になること。

### 2-5. OG 画像の Content-Type を確認する（対応は確認後に判断）

- **根拠**: 375件すべての OG 画像が `application/octet-stream` で配信されている（`og:image:type` の宣言は `image/png`）。Next.js が拡張子なしファイルとして出力し、GitHub Pages が MIME を決められないため。
- **まずやること**: **実害の確認から**。X の Card Validator、Slack・Discord への URL 貼り付けでカードが正常表示されるかを見る。`docs/site-design/` の OGP 記録は画像の見た目の検証のみで、Content-Type の検証は行われていない。
- **問題が再現しなければ対応不要。** 再現する場合のみ、ビルド後スクリプトで `opengraph-image` → `opengraph-image.png` にリネームし、メタタグの URL も揃える。
- **先行指標**: `curl -sI <OG画像URL> | grep content-type` が `image/png` を返すこと。

## Phase 3 — 権威と発見性（1〜2か月）

この段階の施策は**すべて Phase 1 の完了が前提**。中身が薄いページに外部から人を連れてきても効果が出ない。

### 3-1. データセットの公開先を増やす

[backlinks.md](findings/backlinks.md) §5 の優先度順:
1. GitHub の awesome list（`awesome-public-datasets` 等）へ PR（各リストの CONTRIBUTING に従う）
2. Kaggle または Hugging Face Datasets へ `emperors.csv` を公開し、出典欄にサイトと GitHub のリンクを明記
3. Wikidata の各皇帝アイテムへ、本データセットを出典（P854 / P973）として**個別に**追加提案する（一括投稿はしない）
4. 日本語版 Wikipedia は **ノートページで提案し第三者の編集者の判断を仰ぐ**（COI ガイドライン。自分で本文に直接追記しない）
5. Show HN、Reddit の `r/dataisbeautiful`・`r/China` 等へ1回の紹介（`r/AskHistorians` は自己プロモーション禁止のため対象外）

Zenodo DOI は見送り済みの決定のため、この計画には含めない。

### 3-2. 運営者情報を明示する

- **根拠**: E-E-A-T の Authoritativeness が 25/100。著者・運営者の実在性を示す情報が本文にも構造化データにも一切なく、Dataset の `creator` はサイト自身を指す自己言及（`sameAs` なし）。
- **やること**: `/about` に運営者の記載（実名でなくハンドルでもよい）と、GitHub アカウント等への `sameAs` を持つ Organization / Person ノードを追加する。
- **判断が必要な点**: `/about` の「制作者は歴史学の専門家ではありません」という開示は、透明性としては正しい一方 Expertise シグナルを押し下げるトレードオフになっている。**この開示を残すかどうかは方針の問題なので、こちらでは判断しない。** 残す前提なら「専門家ではないが、全件を一次史料で確認し、引用と暦換算の記録を公開している」という検証可能性の側を強調する書き方が両立する。

### 3-3. 構造化データのグラフを結合する

[schema.md](findings/schema.md) に実データ入りの JSON-LD 例あり。Organization ノードの新設、`@id` による WebSite / WebPage / Dataset / Person の相互参照、ランキングページへの `ItemList`、`/timeline` に欠けている WebPage、Dataset の `keywords`・`identifier`（Zenodo DOI の代わりに GitHub リポジトリ URL）。

FAQPage・HowTo は追加しない。
